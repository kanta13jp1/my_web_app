# grill-me スキル

## 目的

実装を始める前に、ユーザーの計画のあらゆる面を徹底的に質問して、
**実装者(私)とユーザーの認識を完全に一致させる**。曖昧な仕様・暗黙の前提・
未決定の設計分岐を全て表面化させ、後戻りコストの高い手戻りを防ぐ。

このスキルの本体は「速く作ること」ではなく「正しく理解すること」。
認識が揃ったと**ユーザー本人が確認するまで、実装コードは一切書かない**。

## 進め方 (厳守ルール)

1. **質問は必ず1つずつ。** まとめて複数聞かない。1問投げたら**回答を待ってから**次へ進む。
2. **各質問に推奨回答を添える。** 「私は A を推奨します。理由は〜。これで良いですか?」の形にし、
   ユーザーが「はい」だけで済むようにする。ただし推奨を押し付けず、代替案も一言添える。
3. **調べれば分かる事実は自分で調べる。** コード・docs・既存実装を先に読み、
   事実確認のための質問でユーザーの時間を奪わない。**決定はユーザーのもの**なので、
   トレードオフのある選択・優先順位・スコープは必ず本人に聞く。
4. **決定木を枝ごとに辿る。** 上流の決定(何を作るか)から下流(どう作るか)へ、
   依存関係の順に1本ずつ解消する。ある決定が他の決定を無効化するなら、上流を先に固める。
5. **一度に踏み込みすぎない。** 1つの論点が片付いてから次の論点へ。話を発散させない。
6. **認識が揃うまで実装しない。** 「これで実装に入って良いですか?」と明示的に確認し、
   ユーザーが GO を出すまでコードを書かない。

## 手順

### 0. テーマの確定

- 引数でテーマが渡されていればそれを対象にする。
- 無ければ最初に「何の計画を詰めますか?」と1問だけ聞く(候補を2-3個添える)。

### 1. 事前調査 (ユーザーに聞く前に)

- 関連コード・docs・既存の類似実装を読み、現状と制約を把握する。
- ここで判明した事実は質問せず、前提として質問文に織り込む
  (例:「既存の X は Y で実装されています。今回もそれに合わせますか?」)。

### 2. グリル (1問ずつ)

以下の観点を、依存順に1つずつ潰す。全部を機械的に聞くのではなく、テーマに関係するものだけ:

- **目的 / 成功条件**: 何が達成できたら「完了」か。誰のどんな課題を解くか。
- **スコープの境界**: やること / やらないこと。今回やらないと決めるものは何か。
- **ユーザー体験**: 入力・出力・エラー時・空状態の挙動。
- **データ / 状態**: どこから来てどこへ保存するか。実データか演出か。永続化の要否。
- **設計の分岐**: 実装方式のトレードオフ(性能 / 保守性 / 工数)。
- **エッジケース / 失敗モード**: 想定外入力、境界値、リカバリ。
- **依存・影響範囲**: 既存機能への影響、破壊的変更の有無。
- **検証方法**: どうやって「正しく動く」と確認するか(テスト / 手動 / E2E)。
- **優先順位 / 段階**: 最小で出す範囲と、後回しにする範囲。

各質問は「**質問 + 推奨回答 + 理由 + (代替案) + 確認**」の1セットで出す。

### 3. 認識のサマリ

- 全論点が片付いたら、**合意した計画を箇条書きで要約**して提示する。
- 「この理解で実装に入って良いですか?」と最終確認する。

### 4. GO 後

- ユーザーが承認したら、初めて実装に着手する。
- 途中で新たな分岐が出たら、勝手に決めずまた1問に戻る。

## アンチパターン (やってはいけない)

- 質問を箇条書きで5個まとめて投げる → **1問ずつに分割する**。
- 推奨回答を出さず「どうしますか?」と丸投げする → **必ず推奨を添える**。
- 調べれば分かることを聞く → **先に読む**。
- 確認を取らずに実装を始める → **GO まで書かない**。
- 論点を発散させて雑談化する → **依存順に1本ずつ**。

## 備考

- この技法は「grill me(=しつこく問い詰める)」として知られる対話パターンの
  自分株式会社向け実装。ファイルは本リポジトリ独自に記述したもの。
- 軽い相談なら普通に会話で足りる。**後戻りコストが高い決定**(新機能の設計・
  スキーマ変更・破壊的変更など)の前に使うと効果が大きい。
