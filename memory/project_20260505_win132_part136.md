## 設計 trade-off (= 採用判断)

1. **SessionStart 採用** (vs PostToolUse / UserPromptSubmit)
   - 1 セッション 1 回 / overhead 最小 / 確実に session 開始時 sync
   - PostToolUse は過剰発火 / UserPromptSubmit は session 中 drift 稀

2. **Daily 03:30 JST 採用** (vs その他時刻)
   - GHA cron 03:00 の 30 分後 = canonical push 後の local pull/apply に余裕
   - SCHEDULE-WAKEUP rule の深夜帯 02:00-06:00 と若干重複だが user 影響最小

3. **silent failure 採用** (vs strict block)
   - Python なし / repo 未 pull / network 障害でも session は起動継続
   - log 記録のみで次回再試行
   - block すると Claude Code 起動不能リスク

4. **Tier 3 が Issue 起票でなく comment** (vs 新規 Issue)
   - 全 user 通知すべき = noise / 既存 #1647 (= Codex Memory + Thread Automations) は rule infra tracking として既存
   - 新 Issue = noise / dedup 困難

## 学び

1. **「GHA / local の隔離」を多層で補完**:
   - Tier 1 (= Claude session に閉じた即時修復)
   - Tier 2 (= local cron / session 外を補完)
   - Tier 3 (= GHA notification / 双方向 awareness)
   - 単一 mechanism では不十分 → 多層化で穴を埋める

2. **「設定ファイル PowerShell 駆動」の柔軟性**:
   - `.claude/settings.json` は Claude Code 公式 config
   - PowerShell hook script で Python invoke + log 記録 + silent failure を全て管理
   - PowerShell は Windows native = 移植性問題なし

3. **「Tier 2 setup script の冪等性」**:
   - 既存 task 検出 → 削除 → 再作成 で `--Install` 何度叩いても OK
   - `--Status` で確認 / `--Uninstall` で削除 / 学習コスト最小

4. **「failure の log 戦略」**:
   - `memory/inject-rules-sync/sync-YYYYMMDD.log` (= Tier 1)
   - `memory/inject-rules-sync/cron-YYYYMMDD.log` (= Tier 2)
   - 別 file で混在せず追跡可 / append-only
