## 真の root cause (= part 123 fix では解決していなかった)

調査で発覚した構造的欠陥:

1. **`blog_posts` table は実際には未使用** — schema migration で作成されたが、T-1 dispatch flow は使わない
2. **schedule-hub `blog.create`** = `addItem(admin, "blog_post", effectiveUserId, ...)` 経由で **`hub_data` table** (source='blog_post' / user_id='system') に書き込み
3. **schedule-hub `blog.auto_publish`** = dev.to + Qiita API に POST するだけで **DB 更新せず** → 投稿成功した記事の `status='posted'` がどこにも記録されない
4. **`hub_data` RLS** = `metadata->>'user_id' = auth.uid()::text` のため `user_id='system'` の row は login user では SELECT 不可
5. = 全フローが「dispatch 後の状態を DB に残さない」設計欠陥

→ part 123 で page を `blog_posts` table query に変えても **table 自体に data がない** ため依然 0 表示.

## 完了 (= 4 軸並列実装)

### 1. EF 拡張 + 2 新規 action (`supabase/functions/schedule-hub/index.ts`)

**(a) `blog.auto_publish` 拡張**: API publish 成功後、`hub_data` row を upsert
- `body.id` 指定時 → 既存 row (= `blog.create` で作った draft) を merge update
- `target_platforms` + `platform_urls` は配列 / map merge (= qiita+devto 別 call で同一 id 参照する workflow に対応)
- `body.id` 未指定時 → 新規 insert
- DB 失敗時は try/catch で publish 結果は返す (= degrade safe)

**(b) `blog.recent_posted` 新規 action** (public read):
- service-role 経由で `hub_data` の `posted` blog_post を返す
- `days` (1-365) + `limit` (1-500) param
- page から auth 不要で call 可能 (= publicActions allowlist 追加)

**(c) `blog.backfill_from_apis` 新規 action** (one-shot backfill):
- `dev.to` `/api/articles/me/published` + Qiita `/authenticated_user/items` から自分の published 記事 fetch
- 既存 `hub_data.metadata.platform_urls` と URL dedup
- 未登録分のみ `metadata.backfilled=true` + `source_api` フラグ付きで insert
- summary に inserted/qiita_fetched/devto_fetched/skipped_dup/skipped_old 返す

### 2. Workflow 修正 (`.github/workflows/blog-publish.yml`)

Step 4 の qiita + devto 別 call に `id: $POST_ID` (= Step 3 register.outputs.post_id) 追加 → EF が正しい `hub_data` row を update する.

### 3. Page 修正 (`lib/pages/tech_blog_tracker_page.dart`)

旧 `_supabase.from('blog_posts').select()` (= 空 list 問題) を削除し、EF `schedule-hub blog.recent_posted` 経由で取得するよう変更. response.data.items を `_scheduleDrafts` にマッピング. 既存 `_isPostedToday` / `_currentStreak` / `_totalPostedDays` / `todayCount` (= part 123 fix) は同 shape のため変更不要.

### 4. 一発 backfill workflow (`.github/workflows/blog-backfill-from-apis.yml`)

`gh workflow run blog-backfill-from-apis.yml -f days=60` で `blog.backfill_from_apis` EF action を呼び出す one-shot workflow. 過去 60 日の dispatch を一括 hub_data 入れる.

## 学び

1. **「page 側 fix」≠「root cause fix」** — part 123 で page 側 union 化したが、実は EF が DB 書いてなかった. **Phase 1 「page 表示異常」で Phase 2 「DB query 拡張」したつもりが、Phase 3 「EF DB write 欠落」が真因だった**. 「fix の階層」を意識する必要.
2. **EF と DB schema の disconnect** — `blog_posts` table 作ったが EF 実装は `hub_data` (= 汎用 generic CRUD table) を使った. **schema-EF 同期 audit** が長期 backlog.
3. **public read action の安全性** — `blog.recent_posted` は service-role bypass で公開. RLS bypass する代わりに「返す columns 限定」(= title / status / posted_at / urls / tags のみ) で安全性確保.
4. **「並列 4 instance 同 file 編集」の rebase pattern** — 本 part で PS#3/#5/#6 並列で同 page + 同 EF を編集 → 2 回 conflict + lint 連鎖. **同 file 並列編集の coordination cross-instance-pr** が次回 candidate.
5. **lint「prefer_const_constructors」の自動修正** — `dart fix --apply` で 18 行 / 4 errors を 1 command で解消. **CI fail → dart fix loop の最短 pattern**.
