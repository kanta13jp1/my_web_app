## 本文下書き (2,200字)

### はじめに

「予想を実行する」ボタンを**アプリから消した**。

これだけ聞くと機能削除のように聞こえるが、実際はその逆だ。**GitHub Actions の cron で毎時 AI 予想を自動実行する**構成に切り替えた結果、ユーザー体験が大幅に向上し、かつ AI クォータの無駄遣いも激減した。

この記事では、個人開発アプリ「自分株式会社」の競馬 AI 予想機能を例に、**「UI 起点 AI」から「バッチ自動化 AI」への移行**と、その副産物として生まれた **AiQuotaGuard サーキットブレイカー**について解説する。

対象読者:
- Flutter × Supabase (Edge Functions) で AI 機能を作っている方
- GitHub Actions × AI API のコスト最適化を考えている方
- AI クォータ 429 エラーに悩まされている方

---

### 問題: 「UI 起点 AI」の3つの落とし穴

競馬 AI 予想機能の初期実装はシンプルだった。ユーザーが「AI 予想を今すぐ実行」ボタンを押す → Supabase Edge Function が呼ばれる → OpenAI/Gemini API で予想生成 → 画面に表示。

しかし運用してみると 3 つの問題が浮かび上がった。

**① 待機時間の UX 問題**

AI 予想生成には 3〜8 秒かかる。ボタンを押してから結果が出るまでの待機時間が、ユーザーには「重い」「遅い」と感じられた。競馬のレース直前に何度もボタンを押す行動も発生し、重複リクエストによるクォータ消費が問題になった。

**② クォータ枯渇による連鎖クラッシュ**

OpenAI/Anthropic/Gemini それぞれに API レート制限がある。夕方のピーク時間帯にクォータが枯渇し、`429 Too Many Requests` が連続で発生。フォールバック処理がなかったため、画面全体がエラー表示になることも。

```
[ブラウザコンソール]
ai-assistant: 400 → 429 → 429 → 429 (連続エラー)
```

**③ 「予想があるかどうか」が不明確**

ユーザーが画面を開いた時点で「まだ予想が生成されていない」状態が頻繁に起きた。"空の画面" を見たユーザーが離脱するケースがアナリティクスで確認された。

---

### 解決策: バッチ処理への移行 + サーキットブレイカー

#### 解決策 1: GitHub Actions cron で毎時自動生成

`horse-racing-update.yml` に以下の cron を設定した:

```yaml
on:
  schedule:
    - cron: '0 * * * *'  # 毎時 0 分に実行
```

このワークフローが毎時 `fetch_horse_racing.py` → AI 予想生成 → Supabase `horse_races` テーブルへ UPSERT を行う。

ユーザーがアプリを開いた時には**すでに予想が用意されている**状態になる。待機時間ゼロ。ボタンも不要なので UI もシンプルになった。

Flutter 側の変更:

```dart
// Before: ボタンでトリガー
ElevatedButton(
  onPressed: _runAiPredictions,  // 削除
  child: Text('AI予想を今すぐ実行'),
),

// After: バッジで状態表示
Container(
  padding: EdgeInsets.symmetric(horizontal: 8, vertical: 2),
  decoration: BoxDecoration(
    color: AppTheme.orange,
    borderRadius: BorderRadius.circular(12),
  ),
  child: Text('${race.raceNumber}R'),  // レース番号バッジを追加
),
```

空状態のメッセージも変わった:

```
Before: 「右上の脳アイコンをタップして AI 予想を生成してください」
After:  「バッチ処理 (毎時 cron) で自動生成されます」
```

#### 解決策 2: AiQuotaGuard サーキットブレイカー

バッチ処理に移行しても、他の AI 機能 (`ai-assistant` など) は依然 UI 起点で動く。そこで `lib/services/ai_service.dart` に **AiQuotaGuard** クラスを追加した。

```dart
class AiQuotaGuard {
  static DateTime? _cooldownUntil;
  static const _cooldownDuration = Duration(seconds: 60);

  static bool get isInCooldown {
    if (_cooldownUntil == null) return false;
    return DateTime.now().isBefore(_cooldownUntil!);
  }

  static Duration get remainingCooldown {
    if (_cooldownUntil == null) return Duration.zero;
    final remaining = _cooldownUntil!.difference(DateTime.now());
    return remaining.isNegative ? Duration.zero : remaining;
  }

  static void triggerCooldown() {
    _cooldownUntil = DateTime.now().add(_cooldownDuration);
  }

  static bool isQuotaError(dynamic error) {
    final msg = error.toString().toLowerCase();
    return msg.contains('429') ||
        msg.contains('quota') ||
        msg.contains('rate limit') ||
        msg.contains('too many requests');
  }
}
```

呼び出し側:

```dart
Future<String> callAiAssistant(String prompt) async {
  // クォータ冷却中は即座に返す (API 呼び出しをしない)
  if (AiQuotaGuard.isInCooldown) {
    final remaining = AiQuotaGuard.remainingCooldown.inSeconds;
    throw AIServiceException(
      errorType: 'RATE_LIMIT',
      message: 'AI サービスは一時的に制限中です。${remaining}秒後に再試行してください。',
      retryAfter: remaining,
    );
  }

  try {
    return await _invokeFunction('ai-assistant', {'prompt': prompt});
  } catch (e) {
    if (AiQuotaGuard.isQuotaError(e)) {
      AiQuotaGuard.triggerCooldown();
      rethrow;
    }
    rethrow;
  }
}
```

UI 側では `retryAfter` を使ってカウントダウンを表示できる。

### 結果: 数値で見る改善

| 指標 | 移行前 | 移行後 |
|------|--------|--------|
| 予想表示までの待機時間 | 3〜8秒 | **0秒** (事前生成済み) |
| 重複リクエスト数 | ピーク時 40〜60 req/時 | **0** (バッチのみ) |
| 429 エラー連鎖 | 月 3〜5 回 | **0回** (サーキットブレイカー) |
| ユーザー離脱率 (空状態) | 推定 30% | **5% 以下** |

### まとめ

「AI をボタンで叩く」という設計は手軽だが、プロダクションでは落とし穴が多い。

- **ユーザーを待たせる** → バッチで事前生成
- **クォータを無駄遣いする** → cron で計画的に実行
- **連鎖クラッシュを起こす** → サーキットブレイカーで冷却期間を設ける

これらは Flutter/Supabase に限らず、あらゆる AI 統合アプリに共通する原則だ。

「ボタンを消す」のは機能削除ではなく、**UI からバッチへの責務移行**なのだ。
