# 個人開発者のコンテンツマーケティング戦略 — dev.to 70本から学んだこと

dev.to に70本投稿した。最初の30本は手書き。残りの40本は AI と並走。この70本で学んだことを全公開する。

## 最初に結論

```
コンテンツは「作る」のではなく「記録する」
実装 → 実録 → 投稿 の3ステップで摩擦がゼロになる
```

手書きで書いたときは「ネタを考える」コストが高かった。AI と並走してから気づいた: **自分がやったことを書けばいい**。ネタは常にある。書く手間が問題だった。

## 70本投稿の実績データ

```
Phase 1-3 (手書き期):   約30本 / 3ヶ月 = 10本/月
Phase 4-10 (AI並走期): 約40本 / 2ヶ月 = 20本/月

平均 views/記事: ~400 (dev.to)
最高 views: 2,100 (Flutter Web SEO 記事)
Follower 増加: 約180名
```

投稿頻度が2倍になった理由は「AI に草稿を書かせる」からではない。**記録サイクルが高速化した**から。

## 「記録する」コンテンツの作り方

### Step 1: 実装する

普通に実装する。コンテンツのことは考えない。

### Step 2: 実録メモを残す

実装が終わったら、5分でメモを書く:

```
- 何を作ったか (1行)
- なぜこのアプローチを選んだか (2-3行)
- はまったポイント (箇条書き)
- 最終的な実装パターン (コードスニペット)
```

このメモが記事の骨格になる。

### Step 3: AI で草稿に展開する

メモを Claude に渡す:

```
以下のメモを dev.to の記事に展開してください。
読者は Flutter / Supabase を使う個人開発者です。

[メモの内容]
```

草稿が出たら、自分の視点とコードを追加して完成させる。全体工数: 30分以内。

## AIによる並行ドラフト生成の仕組み

12インスタンス並行開発環境では、ブログ専任インスタンス (PS#2) が存在する:

```
PS#2 専任タスク:
  - 実装インスタンスの commit から実録を収集
  - JA/EN ドラフトペアを生成
  - blog-publish.yml で dev.to に自動 dispatch
```

これで「実装 → コミット → 記事」が自動的に流れる。記録コストがほぼゼロになった。

## dev.to で伸びるコンテンツの共通点

70本の中で views が高かった記事の共通点:

**1. 具体的なタイトル**

```
❌ 「Supabaseを使った認証の話」
✅ 「Supabase Auth in Flutter: JWT, Magic Links, and OAuth from Scratch」
```

読者は「この記事で何が手に入るか」を3秒で判断する。

**2. 冒頭に結論**

```dart
// 最初にコードを見せる
await supabase.auth.signInWithOtp(email: 'user@example.com');
```

ブログは論文ではない。結論→理由の順で書く。

**3. コードが主役**

テキスト2:コード8 くらいの比率でいい。個人開発者の読者はコードを見に来ている。

**4. 実際に動いているシステムの話**

「〜という設計が良いと思います」より「うちの本番システムで〜が起きた」の方が読まれる。

## 継続する仕組み

70本投稿できた最大の理由は「ルーティン化」:

```
月曜: 実装作業 (コミット単位で記録)
水曜: AI でドラフト生成 (JA/EN ペア)
金曜: dispatch → dev.to 公開
```

週1本ペースが最低ライン。週2本 (JA/EN ペアで実質4本) が理想。

**キーポイント**: ネタを探さない。実装がネタになる。実装していれば書くものは無限に出てくる。

## 個人開発者がコンテンツを続けるべき理由

```
記事 → Follower → 信頼 → ユーザー獲得

vs

広告 → コスト → ROI 不確定
```

コンテンツは資産。広告費は消える。70本の記事は来年も検索される。$0 で作った資産が月 10,000+ PV を生み続ける。

ソロ創業者がコンテンツを書くコストは実は低い。実装しているなら、記録するだけでいい。
