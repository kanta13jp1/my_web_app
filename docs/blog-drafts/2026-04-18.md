## 本文下書き (約 2000 字)

### はじめに

Flutter プロジェクトで「マジックナンバー色」問題は誰もが経験するはずです。
`Colors.blue`、`Colors.orangeAccent`、`Colors.grey` — いつの間にかコード全体に
散らばり、デザイン変更のたびに全ファイルを grep する羽目になる。

自分株式会社 (https://my-web-app-b67f4.web.app/) は Flutter Web + Supabase で構築した
AI 統合ライフマネジメントアプリですが、開発が進むにつれてこの問題が深刻化していました。
`Colors.blue` が何十ファイルにも散在し、ブランドカラー (Indigo/Orange ダークテーマ) と
バラバラな見た目になっていたのです。

今回のセッション (VSCode版#107〜109) で、Claude Code を使って **200 ファイル超の
DESIGN token 一括移行**を実施しました。この記事ではその手法と得られた知見を共有します。

---

### 課題: Off-Brand Colors が散在するコードベース

`docs/DESIGN.md` には自分株式会社のデザインシステムが定義されています:

```
Primary:   #5C6BC0 (Indigo 400)
Secondary: #FF7043 (Deep Orange 400)
Surface:   #1A1A2E (Dark Navy)
On-Surface: #E8EAF6
```

しかし実際のコードには:

```dart
color: Colors.blue,          // → #2196F3  ブランドと乖離
color: Colors.orangeAccent,  // → #FFAB40  近いが不正確
color: Colors.grey,          // → #9E9E9E  コントラスト不足
color: Colors.lightBlue,     // → #03A9F4  ブランドと無関係
```

が 200 ファイル以上に存在していました。手動で直すのは不現実な規模です。

---

### 実装方法: Claude Code による段階的バッチ移行

#### Phase 1: 移行マッピング定義 (VSCode版#107)

まず `DESIGN.md` のトークンと Flutter の `Colors.*` の対応表を作成:

| Flutter Color | DESIGN token hex | 用途 |
|---|---|---|
| `Colors.blue` | `0xFF5C6BC0` | primary |
| `Colors.lightBlue` | `0xFF5C6BC0` | primary (同一扱い) |
| `Colors.orangeAccent` | `0xFFFF7043` | secondary |
| `Colors.yellow` | `0xFFFFD54F` | warning/accent |
| `Colors.grey` | `0xFFB0B0B0` | on-surface muted |

#### Phase 2: 自動置換スクリプト生成 (VSCode版#108)

Claude Code に以下のプロンプトを渡しました:

```
lib/ 配下の全 .dart ファイルを対象に、
DESIGN.md のトークンマッピングに従って
Colors.blue → Color(0xFF5C6BC0)
Colors.lightBlue → Color(0xFF5C6BC0)
Colors.orangeAccent → Color(0xFFFF7043)
Colors.yellow → Color(0xFFFFD54F)
に一括置換してください。
ただし import 文・コメント・文字列リテラルは除外すること。
```

Claude Code は grep で対象ファイルを列挙し、Edit ツールで 118 ファイルを順次書き換えました。
重要なのは「1 ファイルごとに flutter analyze を確認しながら進む」設計にしたことです。
途中でコンパイルエラーが出ても即座に検知できます。

#### Phase 3: Grey と残余カラーの処理 (VSCode版#109)

`Colors.grey.shade400` のような shade 付き参照が難関でした。
単純な文字列置換では対応できないため、Claude Code が個別に判断:

```dart
// Before
color: Colors.grey.shade400,

// After (shade400 = approximately 0xFFBDBDBD)
color: const Color(0xFFBDBDBD),
```

`Colors.grey.shade800` → `0xFF424242` のように shade 値ごとに適切な hex を選定。
VSCode版#109 で 81 ファイルのこの処理を完了しました。

---

### 詰まったポイント

#### 1. `Color(0xFF...).shadeN` 構文エラー

最初のバッチで以下のようなコードが生成されてしまいました:

```dart
color: Color(0xFFB0B0B0).shade200, // ← コンパイルエラー!
```

`Color` クラスには `.shade` メソッドがなく、`MaterialColor` のみが持ちます。
flutter analyze で即座に検知し、正しい hex 値に差し替えて解決しました。

#### 2. PdfColors vs Color の混在

`pdf` パッケージを使う箇所では `PdfColors.grey` を使うべきところを
`Color(0xFFB0B0B0)` に置換してしまうケースが発生。
ファイル冒頭の import を確認してから置換するルールを追加しました。

#### 3. require_trailing_commas lint エラーの連鎖

大量の Edit により trailing comma が抜けた箇所が 36 件発生。
PS版#136 で `dart fix --apply` を一括実行して解消しました。
これはバッチ処理特有の副作用で、最後にまとめて修正するのが効率的です。

### 結果と効果

| 指標 | Before | After |
|---|---|---|
| Off-brand Colors.* 参照 | 200+ 箇所 | 0 箇所 |
| DESIGN token 準拠率 | ~40% | ~100% |
| flutter analyze エラー | 0 (維持) | 0 (維持) |
| 作業時間 (推定手動) | 8〜12 時間 | 約 2 時間 (Claude Code) |

視覚的にも一貫性が大幅に向上し、ホーム画面・AI大学・管理画面の
ブランドカラーが統一されました。

---

### まとめ

Claude Code を使った大規模リファクタリングのポイントは:

1. **段階的バッチ処理** — 一度に全ファイルを処理せず、カテゴリ別に分ける
2. **flutter analyze を各フェーズで確認** — エラーを早期検知
3. **shade 参照は個別処理** — 単純置換では対応できない
4. **最後に lint 一括修正** — `dart fix --apply` で trailing comma 等を整理

DESIGN.md によるデザイントークン管理 + Claude Code による一括適用の組み合わせは、
大規模 Flutter プロジェクトのデザイン統一に非常に有効でした。
同じ課題を抱えている方の参考になれば幸いです。
