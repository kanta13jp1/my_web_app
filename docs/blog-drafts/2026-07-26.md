### はじめに

「自分株式会社」というコンセプトで、Flutter Web + Supabase を使った個人SaaSを開発しています。最近、自分のプロジェクトで面白いことが起きました。Claude Code (AI コーディングアシスタント) が、私が指示もしていないのに GitHub Actions のCI/CDパイプラインを自動最適化してくれたのです。

今回はその一週間のログをもとに、**AI駆動開発でCI/CDがどう変わったか**を紹介します。

### 実装内容：何が変わったのか

#### 1. Flutter pub キャッシュの追加で ビルド時間 30-60秒 → 3-5秒

今週の最大の改善がこれです。`deploy-dev.yml` と `deploy-staging.yml` に `actions/cache@v6` を使った Flutter pub キャッシュを追加しました。

```yaml
- name: Cache pub dependencies
  uses: actions/cache@v6
  with:
    path: ~/.pub-cache
    key: ${{ runner.os }}-pub-${{ hashFiles('**/pubspec.lock') }}
    restore-keys: |
      ${{ runner.os }}-pub-
```

**Before:** `flutter pub get` が毎回パッケージをダウンロードして 30〜60秒かかっていた
**After:** キャッシュヒット時は 3〜5秒で完了

月間の推定削減量は **約90〜270 ubuntu-minutes**。地味に見えますが、積み重なると有料プランのコスト削減に直結します。しかもこのパターン、`ci.yml` ではすでに使っていたのに、deploy 系のワークフローに適用し忘れていました。Claude Code がそのギャップを自動的に検出して修正してくれました。

#### 2. MCP Smoke テストのキャンセル処理を修正

`tools-hub-mcp-smoke.yml` では別の問題がありました。ステートレスな HTTP プローブなのに `cancel-in-progress: false` になっていたため、複数のワークフローが同時に走る状況で不要なリソース消費が発生していました。

さらに、ジョブがキャンセルされた場合に `STATUS="critical"` と誤記録されてしまい、proactive_diagnostics がアラートを出してしまうバグもありました。

修正内容：
- `cancel-in-progress: false → true`（ステートレス HTTP プローブなのでキャンセル安全）
- `JOB_CANCELLED=cancelled()` でキャンセルを検出し `STATUS="skipped"` に統一
- `SUMMARY` の `SMOKE_OUTCOME` に `:-cancelled` フォールバックを追加

これにより、誤アラートがゼロになりました。

#### 3. grill-me スキルの追加

今週マージされた PR #4324 では、`grill-me` という新しい Claude Code スキルも追加されました。これは実装に入る前にユーザーの計画や意思決定を1問ずつ厳しく問い詰め、認識が完全に揃うまでインタビューするスキルです。

「作ってから違った」を防ぐための壁打ち機能で、AI と一緒にプロダクト開発する際の意思決定の質を上げることを目的としています。

### 詰まったポイント

**キャンセル検出の落とし穴**

GitHub Actions のキャンセル検出は `cancelled()` 関数を使いますが、これを使うには `if: always()` と組み合わせる必要があります。そうしないと、ジョブがキャンセルされた時点でその後のステップが実行されません。

```yaml
- name: Record result
  if: always()
  run: |
    if [ "${{ cancelled() }}" = "true" ]; then
      STATUS="skipped"
    fi
```

**pubspec.lock のハッシュキー**

キャッシュキーに `hashFiles('**/pubspec.lock')` を使うことで、依存関係が変わったときだけキャッシュが無効化されます。`pubspec.yaml` ではなく `pubspec.lock` を使うのがポイントで、これにより再現性も保たれます。

### AI駆動開発の所感

今回の最適化は私が明示的に指示したものではなく、Claude Code が定期的なCI/CD監査ワークフロー（`docs/ci-cd-audit/`）の結果をもとに自律的に実施しました。

人間がやると「まあ後でいいか」と後回しにしがちな細かい最適化を、AIは淡々とこなしてくれます。特に「ci.yml には既にあるのに deploy 系には適用されていない」というパターンの発見は、コードベース全体を俯瞰できるAIならではの仕事です。

一方で、AIが自律的に変更を加えていくため、**変更の意図やトレードオフを理解する人間のレビュー**が必要だとも感じています。自動化は強力ですが、最終的な品質保証は人間が担う必要があります。
