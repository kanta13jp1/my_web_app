### はじめに

自分株式会社 (Flutter Web + Supabase) で先週リリースした機能の中で、個人的に一番手応えを感じたのが **Social Commerce Hub への多段階承認ワークフロー追加** です。

割引や特典付与は「ビジネス上の損失」に直結するため、承認フローを適切に設計しないとオペレーションが崩壊します。今回は Supabase Edge Function (Deno) に純粋関数として実装し、テスト 6/6 パス・後方互換を維持した形で本番投入できました。

この記事では、実装アーキテクチャ・詰まりポイント・ソロ創業者として並行してインフラ運用体制も整えた話をまとめます。

### 実装方法

#### 1. 多段階承認の要件定義

割引承認には以下の 4 ステップを設けています:

| ステップ | 担当 | 発動条件 |
|----------|------|----------|
| Step 1 | Manager | 任意の割引申請 |
| Step 2 | Finance | 割引率が閾値超 or 無償提供あり |
| Step 3 | Legal | 特権付与 (privilege grant) を含む場合 |
| Step 4 | CEO | 大口割引 or 複数条件該当 |

これをコードで表現するために、2 つの純粋関数を設計しました。

```typescript
// supabase/functions/_shared/multi_step_approval_workflow.ts

export function buildMultiStepApprovalWorkflow(
  request: DiscountApprovalRequest
): ApprovalWorkflow {
  const steps: ApprovalStep[] = [];

  // Step 1: Manager は常に必要
  steps.push({ role: "manager", status: "pending" });

  // Step 2: Finance — 割引が大きい or 無償提供
  if (request.discount_rate > FINANCE_THRESHOLD || request.free_offer) {
    steps.push({ role: "finance", status: "pending" });
  }

  // Step 3: Legal — 特権付与
  if (request.privilege_grants?.length > 0) {
    steps.push({ role: "legal", status: "pending" });
  }

  // Step 4: CEO — 大口
  if (request.discount_rate > CEO_THRESHOLD) {
    steps.push({ role: "ceo", status: "pending" });
  }

  return { steps, current_step_index: 0, status: "held_for_approval" };
}

export function applyApprovalStepDecision(
  workflow: ApprovalWorkflow,
  decision: StepDecision
): ApprovalWorkflow {
  // 現在ステップに決定を適用し、監査イベントを追加
  const updated = { ...workflow };
  updated.steps[workflow.current_step_index].status = decision.approved
    ? "approved"
    : "rejected";

  if (decision.approved) {
    updated.current_step_index += 1;
    if (updated.current_step_index >= updated.steps.length) {
      updated.status = "approved"; // 全ステップ通過
    }
  } else {
    updated.status = "rejected";
  }

  // 監査イベント + admin_approval_requests 通知イベント emit
  updated.audit_events = [
    ...(workflow.audit_events ?? []),
    { ...decision, timestamp: new Date().toISOString() },
  ];

  return updated;
}
```

#### 2. Edge Function への組み込み

`social-commerce-hub/index.ts` では、既存の単一ステップ承認フローを後方互換で残しつつ、新しいワークフローを分岐させています。

```typescript
// 後方互換フォールバック
if (!request.approval_workflow) {
  return handleLegacySingleStepDecision(request, decision);
}

// 多段階フロー
const updatedWorkflow = applyApprovalStepDecision(
  request.approval_workflow,
  decision

```

#### 3. テスト戦略 (Deno Test)

純粋関数として設計したことで、外部依存なしに 6 ケースを網羅できました:

- 基本フロー (manager のみ通過)
- Finance ステップ追加 (割引率超)
- Legal ステップ追加 (特権付与)
- CEO ステップ追加 (大口割引)
- 途中 reject → workflow status = rejected
- 後方互換 (approval_workflow なし)

### 詰まったポイント

#### 後方互換の担保

既存の `discount_approval.request` イベントには `approval_workflow` フィールドがありません。新しいフローを追加する際、フィールドの有無で分岐する設計にすることで、既存データへの影響ゼロを達成しました。

```typescript
if (!request.approval_workflow) {
  // 旧フロー: そのまま通す
}
```

この "null チェックによる後方互換" パターンは、Edge Function のスキーマレス性を活かした実用的なテクニックです。

#### 純粋関数設計の恩恵

Edge Function はステートレスなので、ワークフロー状態は DB に持たせる必要があります。`buildMultiStepApprovalWorkflow` と `applyApprovalStepDecision` を副作用なしの純粋関数にすることで:

- Deno Test でモック不要
- Edge Function 本体とのインターフェースが明確
- 将来的に他の Edge Function から再利用可能

という恩恵を得られました。

#### GHA cron の冗長排除

今週の `ci: 冗長フロー自動最適化` コミットで、GitHub Actions の concurrency グループを 2 フローに追加しました。同一ブランチへの連続 push でキューが詰まる問題を解消しています。

```yaml
concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true
```
