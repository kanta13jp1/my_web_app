### はじめに

2026年5月25日、Anthropicが「**Dreaming**」という研究プレビューを発表した。

概要を一言で言えば「AIエージェントの記憶をセッション間で自動整理（重複削除・古いエントリーの剪定）する機能」だ。

これを見て私は思った。

**「これ、6ヶ月前から自分で作って使ってる。」**

インディー開発者として「自分株式会社」（Flutter Web + Supabase + Firebase Hosting）を一人で運営しながら、私はKarpathy式「第二の脳」を自分のSaaSに完全統合してきた。その中心にあるのが、今日紹介する **memory hygiene パイプライン** だ。

---

### 実装方法

#### Karpathy 4サイクルとは

[Andrej Karpathy](https://karpathy.ai/) が提唱する「第二の脳」の運用サイクルは4フェーズからなる：

```
Ingest → Compile → Query → Lint
```

私はこれを自分のリポジトリに100%実装し、2026年5月時点で「part 132」までのdogfoodを完了している。

#### `[MEMORY-DECAY]` ルール — 自社実装の核心

自分株式会社のClaude Code設定（`~/.claude/hooks/inject-rules.txt`）には以下のルールが毎ターン注入される：

```
[MEMORY-DECAY]
- 30+ day reference 0 のエントリー → consolidate対象
- 200+ entries → MEMORY_<period>.md に分割
- 月1回 consolidate-memory skill でcleanup
```

これは**Anthropic DreamingのDuplicate merge + Stale entry pruneと完全に同じ概念**だ。

#### `consolidate-memory` Skill

`scripts/knowledge_vault_lint.py` (part 105実装) と組み合わせ、以下を自動化している：

```python
# 疑似コード
for note in memory_vault:
    if note.last_referenced_days > 30:
        candidates_for_consolidation.append(note)
    if len(memory_vault) > 200:
        archive_to_period_file(note)
```

`/consolidate-memory` skillを手動実行すると：
1. `memory/MEMORY.md` の重複エントリー検出・マージ
2. 30日以上参照なしのエントリーをアーカイブ
3. `MEMORY_<YYYYMM>_archive.md` に分割保存
4. Health Scoreレポート生成

#### Lint サイクル（`scripts/knowledge_vault_lint.py`）

毎週cronで自動実行されるLintは：
- Orphan note検出（どこからも参照されていないファイル）
- Broken wikilink検出
- Duplicate H1タイトル検出
- Missing index entries検出
- **Health Score算出**（`/100`）

今週のHealth Score: **87/100**（major issues: 0, minor: 3）

#### Compile サイクル（`scripts/wiki_compile.py`）

part 132で完成したCompileサイクルは：
- `memory/vault/` の全Atomic Noteを走査
- `docs/concepts/` の概念ページを自動再生成
- `docs/INDEX.md` のマスターインデックスを自動更新

**CLAUDE.md はかつて463行あったが、今は80行**。残りはすべて `docs/` 以下に分散され、LLMが必要に応じて参照する構造になっている。

### 詰まったポイント

#### 1. memoryの「腐敗」問題

最初の頃、`memory/MEMORY.md` はどんどん肥大化していった。古い判断、obsoleteなコンテキスト、重複したルールが積み重なり、200行を超えると参照精度が落ちてきた。

解決策は「本棚の定期整理」と同じ発想だった。**読まれていない本（30日参照なし）はアーカイブへ、本棚が溢れそう（200件超）なら別の棚（期間別ファイル）へ移す。**

#### 2. Lint vs Compile の順序

当初、CompileをLintより先に実行していた。するとbroken wikilinkが新しい `docs/INDEX.md` に取り込まれてHealth Scoreが悪化するという問題が起きた。

正しい順序は **Lint → Fix → Compile**。現在はGHAのcronで自動的にこの順序を維持している。

#### 3. CLAUDE.md 463行問題

すべての指示をCLAUDE.mdに書いていた時期があった。トークンを無駄に消費し、LLMが「今のタスクに関係ない」情報を読み続ける羽目になっていた。

Karpathyが言う「第二の脳は必要な時に必要な情報を取り出せること」の意味を体感した。今は**80行のポインターハブ**として機能し、残りは `docs/` の各Principleファイルに分散している。

### Anthropic Dreaming との比較

| 軸 | Anthropic Dreaming | 自社実装 |
|---|---|---|
| 重複検出 | API経由（research preview） | `knowledge_vault_lint.py` + `consolidate-memory` skill |
| 古いエントリー剪定 | `stale entry prune` | `[MEMORY-DECAY]` 30日ルール |
| ポータビリティ | portable stores | `MEMORY_<YYYYMM>_archive.md` |
| 監査ログ | audit logs | git commit history + `_lint_report.json` |
| 実装時期 | 2026年5月 research preview | **2025年11月〜（6ヶ月以上先行）** |
| スコープ | enterprise / API | **個人CEO + 2-instance fleet** |

重要な違いは**スコープ**だ。AnthropicのDreamingはenterpriseチーム・API中心の設計。私の実装は**個人CEO（一人）がfilesystem + git + GHAで運用するオフラインファースト設計**。

どちらが優れているかではなく、**「個人開発者が先にニーズを見つけ、先に実装できた」という事実が重要**だと思う。大企業が「research preview」を出す頃には、インディー開発者は既に半年以上の運用実績を持っている。
