### はじめに

個人開発で最も時間を奪われるのは「CI が詰まって PR がマージできない」状況です。

Flutter Web + Supabase + GitHub Actions で構成された「自分株式会社」(https://my-web-app-b67f4.web.app/) では、ユーザー数 37 名・機能リクエスト 53 件を抱えながら日々開発を続けています。AI エージェント（Claude Code + Codex CLI）を使って開発速度を上げているぶん、CI ゲートの詰まりが発生すると一気に手が止まります。

今週（2026-05-29 週）は **v21 5層構造防止仕様 (Z-DD)** を策定し、**同日中の自然回復** を初めて実証しました。本記事ではその仕組みと教訓を共有します。

---

### 実装方法

#### 1. PR Gate 詰まりのパターン分類

GitHub Actions の PR Gate が詰まる原因は大きく3種類です。

| パターン | 原因 | 頻度 |
|----------|------|------|
| Body Patch 漏れ | PR 作成時に Declaration Body が空になる | 高 |
| Close/Reopen ループ | ゲート判定キャッシュが古い状態で固着 | 中 |
| Concurrency race | 複数の bot が同一 PR を同時操作 | 低 |

最も厄介なのは **Body Patch 漏れ** です。AI エージェントが PR を作成するとき、本文フィールドに必要なメタデータ（チェックリスト・タスク宣言）を含め忘れると、ゲート判定が永遠に失敗し続けます。

#### 2. Z-DD: 5層構造防止仕様

v21 で導入した Z-DD (Zero-Drift Declaration) は以下の5層で構成します。

```
Layer 1: PR テンプレート強制 (.github/pull_request_template.md)
Layer 2: bot 作成 PR への Body Patch workflow
Layer 3: ゲートチェック前の Declaration 存在確認
Layer 4: Close/Reopen による強制リフレッシュ
Layer 5: 失敗後 72h 以内の自動リトライ (指数バックオフ)
```

**Layer 4 の Close/Reopen パターン** が今回の核心です。GitHub Actions は PR のオープン時にゲート判定をリセットするため、ゲートが固着した場合は PR を一度クローズしてすぐ再オープンすることでキャッシュを強制フラッシュできます。

```yaml
# .github/workflows/gate-recovery.yml の該当部分
- name: Close and reopen PR to refresh gate
  env:
    GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}
  run: |
    gh pr close $PR_NUMBER
    sleep 3
    gh pr reopen $PR_NUMBER
```

#### 3. WBS 自動リバランス × AI ベンチマーク計画

Codex CLI は今週 **asset-management ロードマップの WBS** を自動リバランスしました。具体的には：

- タスク優先度の再スコアリング（AI モデルベンチマーク計画を組み込み）
- video pipeline secret readiness gate (#1724) のブロッカー解除
- 現実的なスケジュール（過去の実績速度から逆算）への自動修正

Codex と Claude Code の役割分担は明確にしています。**Codex = 非同期実装・ドキュメント整理**、**Claude Code = 対話的設計・アーキテクチャ判断** です。この分業により、人間 1 人が複数人分の実装速度を維持できています。

### 詰まったポイント

#### video pipeline の secret 管理

video pipeline (#1724) で最も詰まったのは **GitHub Actions の secret readiness gate** です。シークレットが設定される前にワークフローが走ると、エラーではなく「空文字で処理続行」という最悪のパターンになります。

対策として **secret 存在チェックをゲートの最初に置く** パターンを導入しました。

```yaml
- name: Check required secrets
  run: |
    if [ -z "${{ secrets.VIDEO_API_KEY }}" ]; then
      echo "::error::VIDEO_API_KEY is not set"
      exit 1
    fi
```

このパターンは単純ですが、抜けていることが多いです。CI が「成功したように見えて実は何もしていない」バグを防ぐ最初の砦です。

#### Karpathy Compile サイクルのタイミング

wiki compile (Karpathy Compile cycle) は毎日 18:05 UTC に自動実行されますが、その直前に大量の CS チェックログが入るため、コンパイル結果に古いデータが混入するケースがありました。

解決策: **CS チェックの書き込みロック期間（17:50〜18:10 UTC）** を設けて、compile 実行中の同時書き込みを禁止しました。

### まとめ

今週の主な成果：

1. **Z-DD v21**: PR Gate の5層防止仕様を策定、同日自然回復を初実証
2. **WBS リバランス**: Codex が現実的なスケジュールに自動修正
3. **secret readiness gate**: video pipeline のブロッカー解除

AI エージェント2台体制は「速く動く」ために有効ですが、その速さが CI への負荷増加につながります。今週の教訓は「CI ゲートの堅牢化は AI 導入と同時に行うべき」です。

個人開発でも、CI をちゃんと守ることが長期的な開発速度の維持につながります。引き続き build in public で進捗を共有していきます。
