### はじめに

個人開発のライフマネジメントアプリ「自分株式会社」（Flutter Web + Supabase）を1人で作り続けている。Notion・Evernote・MoneyForward・Slack・X・Amazonなど21社の競合サービスを1つに統合するという、どう考えても無謀なプロダクトだ。

今週は開発上の大きなマイルストーンを達成した。「**EF-CAP-50**」——Supabase Edge Functionの本数を50本以下に抑えるというアーキテクチャ制約への到達だ。最大85本まで膨れ上がっていたEdge Functionを、35本もの削減に成功した。

### 実装方法

#### なぜEdge Functionが85本まで増えたのか

機能追加の初期フェーズでは「1機能 = 1 Edge Function」という素朴な実装が続いた。音声処理、動画会議管理、ポッドキャスト、音楽プレイリスト、スクリーンレコーダー……全て独立したEdge Functionとして実装されていた。

問題はSupabaseの無料プランのEF制限と、コールドスタートの頻発だ。使用頻度の低いEFはキャッシュから外れ、毎回数百msのコールドスタートが発生する。85本全てをウォームな状態に保つのはコスト的に不可能だった。

#### Hubパターンの設計

解決策として「Hubパターン」を採用した。機能カテゴリごとに「Hub」EFを1本作り、その内部で `action` パラメータによってルーティングする設計だ。

```typescript
// media-hub/index.ts
Deno.serve(async (req) => {
  const { action, ...params } = await req.json();
  
  switch (action) {
    case 'podcast.episodes': return handlePodcastEpisodes(params);
    case 'playlist.list': return handlePlaylistList(params);
    case 'recording.start': return handleRecordingStart(params);
    case 'gallery.upload': return handleGalleryUpload(params);
    // ...
  }
});
```

今週だけで以下のHubマイグレーションを完了させた:

| 統合前 (個別EF) | 統合後 (Hub) | 削減数 |
|----------------|-------------|-------|
| audio-effects-processor, screen-recorder, podcast-manager, music-playlist-manager, photo-gallery-manager | **media-hub** | 5→1 |
| carbon-tracker, travel-planner, appointment-scheduler | **lifestyle-hub** | 3→1 |
| social-scheduler, pet-care, recipe-manager | **schedule-hub** | 3→1 |
| gift-manager, wallet, loyalty, emergency, donation | **commerce-hub** | 5→1 |
| social-feed, workflow, event, address, notification, inventory, form, sitemap, memo | **core-hub** | 9→1 |

合計: 25本のEFを5本のHubに統合。EF数 85→50本を達成。

#### 同時実装: notification.broadcast_release

EF整理と並行して、`notification.broadcast_release` アクションも `core-hub` に追加した。新機能リリース時に全ユーザーへのプッシュ通知を一括送信できる機能だ。これによりリリースノートの周知が自動化された。

```typescript
case 'notification.broadcast_release': {
  const { version, highlights } = params;
  const users = await supabase.from('profiles').select('id, push_token');
  await Promise.all(users.data.map(u => sendPush(u.push_token, {
    title: `v${version} リリース`,
    body: highlights.join(' / ')
  })));
  return new Response(JSON.stringify({ sent: users.data.length }));
}
```

### 詰まったポイント

**Deno lintの `no-duplicate-case` エラー**: `media-hub` でpodcastのcaseを重複定義してしまい、CIが失敗した。Hub化で1ファイルに多数のcaseをまとめると、重複定義を見落としやすい。IDEのswitch文ハイライトを頼りに手作業で修正した。

**マイグレーションファイルの命名衝突**: 複数インスタンスで並行開発しているため、同日のマイグレーションファイル番号が衝突することがある。`063000`, `092000`, `093500`, `095000` の4件をrepair listに追加して回避した。

**`no-duplicate-case` はflutter analyzeでは検出できない**: DartのリントとDenoのlintは別物。EFのDeno codeは`deno lint`を必ず通す必要があるが、WEB版インスタンスはローカルCLIが使えないため、VSCode版にcross-instance-prで検証依頼する仕組みを整備した。

### まとめ

Hubパターンによるリファクタリングは単なるEF数削減ではない。コールドスタートの減少、デプロイ単位の集約、モジュール内でのコードの凝集度向上という3つの恩恵をもたらした。

「1機能 = 1 EF」という初期の設計が負債になった経験から学んだのは、「共通のライフサイクルを持つ機能は同じ場所に置く」というシンプルな原則だ。これはマイクロサービスの粒度問題と本質的に同じ。適切な「Hub」の境界を引くことが、スケーラブルなサーバーレスアーキテクチャの鍵だった。
