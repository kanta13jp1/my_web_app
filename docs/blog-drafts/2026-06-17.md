## 本文下書き (約2000字)

### はじめに

「家賃・光熱費・通信費など毎月かかる固定費を、コードを1行も書かずにUIから登録して、資金繰りの見込み残高に自動反映したい」

これは多くの個人開発者・副業ワーカーが感じるニーズです。自分の場合、Flutter Webで作っている自分株式会社アプリ（https://my-web-app-b67f4.web.app/）の資産管理ページで、家賃/KDDI/水道/ガスの固定費が約8箇所にハードコードされていました。新しい固定費が増えるたびにコードを修正してデプロイする必要があり、明らかにスケールしません。

今週、この問題を根本から解決するデータ駆動モデルとUIを実装しました。本記事では設計の考え方から実装の詳細、詰まったポイントまでをまとめます。

### 実装方法

#### Step 1: データモデル設計 (PR #3452)

まずハードコードされた固定費をデータとして扱えるように、`AssetRecurringFixedCost` モデルを定義しました。

```dart
class AssetRecurringFixedCost {
  final String id;
  final String name;       // 家賃、KDDI、水道 など
  final double amount;     // 月額
  final int transferDay;   // 振替日 (1〜28)
  final String period;     // monthly / bimonthly など
  final String? sourceAccount; // 振替元口座
}
```

ポイントは `appliesToMonth(DateTime month)` メソッドです。毎月の場合は常に `true`、隔月の場合は基準月から計算して `true/false` を返します。

永続化には `AssetRecurringFixedCostStore` を作り、`asset_recurring_fixed_costs_v1` というキーでローカルに保存しつつ、Supabase の `asset_pref_mirror` テーブルに全量 upsert する設計にしました。これにより端末間の同期が自動的に行われます。

#### Step 2: 資金繰りへの自動計上

`buildWorkbook(recurringFixedCosts:)` で当月に該当する固定費を自動的に utility 負債として計上します。二重計上防止のロジックが重要で、「同名または同IDの口座がすでに存在する場合はスキップ」する条件を追加しました。

```dart
// 二重計上防止
final alreadyExists = liabilities.any(
  (l) => l.name == cost.name || l.id == cost.id,
);
if (!alreadyExists) {
  _addLiability(cost);
}
```

#### Step 3: UIウィジェットの実装 (PR #3457)

資産管理ページが肥大化しないよう、UIは独立ウィジェットとして切り出しました。

- **`RecurringFixedCostCard`**: 一覧表示 + 追加/編集/削除ボタン
- **`RecurringFixedCostEditorDialog`**: 名称/月額/振替日/周期/振替元の入力フォーム + バリデーション

ページ本体では `_recurringFixedCosts` という状態を持ち、起動時にローカルストレージから読み込み（空の場合はサーバーのミラーから復元）、変更のたびに `asset_pref_mirror` へ upsert します。

```dart
// 起動時ロード（ローカル優先 / ローカルが空ならミラー復元）
final local = await RecurringFixedCostStore.load();
if (local.isEmpty) {
  final mirror = await _fetchMirrorFromSupabase();
  setState(() => _recurringFixedCosts = mirror);
} else {
  setState(() => _recurringFixedCosts = local);
}
```

#### Step 4: キャッシュフロー予測 v2 (PR #3419)

定期固定費と合わせて、キャッシュフロー予測カードも v2 にアップデートしました。

- **ホライゾン切替**: 3/6/12ヶ月のChoiceChipで表示期間を変更可能
- **安全証拠金ライン**: ¥10,000を下回る月を視覚的に警告
- **予算実績比較**: カテゴリ別に予算と実績を比較できるビューを追加

### 詰まったポイント

#### 1. ミラー同期の「ローカル優先 vs サーバー優先」問題

端末AでデータをローカルDBに保存し、端末Bで初回起動した際にどちらを優先するかが問題でした。「ローカルに登録があれば上書きしない安全側」という方針を取りました。これはリボ設定v1と同じポリシーで、過去の実装から学んだ教訓です。

#### 2. 寛容な `fromJson` パース

サーバーから返ってくるデータが必ずしも正しい形式とは限りません。以下のケースは黙って破棄する寛容なパースを実装しました：

- 名称が空
- 金額が0以下
- 振替日が1〜28の範囲外

これにより、古いデータやマイグレーション後のデータでもクラッシュしなくなりました。

#### 3. テスト専用注入

WidgetTestでモックデータを注入できるよう、`debugInitialRecurringFixedCosts` パラメータを追加しました。本番コードに影響を与えずにテストが書けるこのパターンは、Flutter Webのテストで非常に有効です。

```dart
// テストでのみ使用
RecurringFixedCostCard(
  debugInitialRecurringFixedCosts: [
    AssetRecurringFixedCost(name: '家賃', amount: 80000, ...),
  ],
)
```

### まとめ

今週の主要な成果をまとめます：

1. **定期固定費のデータ駆動モデル実装** — コードを触らずにUIから固定費を登録・管理可能に
2. **端末間ミラー同期** — Supabase の `asset_pref_mirror` を使ったローカル優先同期
3. **キャッシュフロー予測 v2** — ホライゾン切替 + 安全証拠金ライン
4. **カテゴリ別予算実績比較** — 月次の予算管理が格段に見やすく
5. **更新バナーの即時確認** — 起動直後 + 前面復帰時にバージョンチェックを追加

個人開発でも「データ駆動 + ミラー同期」の設計パターンを使うことで、コードを修正せずにビジネスロジックを変更できる柔軟性が生まれます。ぜひ参考にしてみてください。

実際のアプリは https://my-web-app-b67f4.web.app/ で動作確認できます。
