# Notion API レート制限の限界と解決策 — 毎秒3リクエストの壁を個人開発者が突破する方法

## 「Notion API を叩いたら 429 が返ってきた」

Notion でライフログを自動化しようとしたことがあるだろうか。

健康データを Apple HealthKit から自動取得してデータベースに書き込む。副業の収入を Stripe Webhook で自動記録する。毎日のタスクを GitHub Issues と同期する。

試みた人はわかるはずだ。すぐに **HTTP 429 (Too Many Requests)** という壁にぶつかる。

---

## Notion API のレート制限、正確に理解する

Notion の公式ドキュメントによると:

> **Average of 3 requests per second per integration token**

これは「平均」という言葉が曲者だ。瞬間的なバーストは許容されるが、継続すると 429 が返る。

具体的に何が問題になるか:

| ユースケース | 必要なリクエスト数 | 問題 |
|-------------|-------------------|------|
| 30日分のヘルスデータ書き込み | 30+ req (1行/日) | 10秒以上かかる |
| 習慣トラッカー (10項目 × 30日) | 300+ req | 100秒以上かかる |
| 収支データ月次インポート | 50-200 req | バースト → 429 |
| 複数DB横断クエリ | ページ数 × テーブル数 | すぐ上限 |

### ブロック数制限も重なる

API のレート制限だけでなく、1ページあたり **1000ブロック制限** もある。長い日記や大量データをページに書き込もうとすると、途中でエラーになる。

## 一般的な「解決策」とその限界

### 解決策1: キューイング + 指数バックオフ

```python
import time
import random

def notion_request_with_backoff(fn, max_retries=5):
    for attempt in range(max_retries):
        try:
            return fn()
        except Exception as e:
            if "429" in str(e):
                wait = (2 ** attempt) + random.uniform(0, 1)
                time.sleep(wait)
            else:
                raise
    raise Exception("Max retries exceeded")
```

**限界**: 待機時間が積み重なる。30分の同期処理が2-3時間になることも。

### 解決策2: バッチ書き込み

Notion API は1リクエストで複数ブロックをまとめて書ける。100ブロックを1リクエストに圧縮すれば理論上100倍効率化。

**限界**: 1リクエストのペイロードサイズ制限 (2000ブロック) + 子ページの場合は別リクエスト必要。

### 解決策3: キャッシュ + 差分同期

全データを書き込まず、前回との差分だけ更新する。

**限界**: 差分検出ロジックが複雑になる。Notion DB のバージョン管理は貧弱で衝突が起きやすい。

---

## なぜこれらの「解決策」では根本的に解決しないのか

個人ライフログに Notion API を使う本質的な問題は、**Notion の設計思想がチームのドキュメント管理用**であることだ。

| チームの Notion | 個人ライフログ |
|----------------|---------------|
| 人間がドキュメントを書く | プログラムがデータを書く |
| 1日数十回の書き込み | 1日数百〜数千回の書き込み |
| 読む人がいる | 分析ツールが読む |
| データ構造が変わりにくい | スキーマが頻繁に進化する |

個人ライフログには **データベース** が必要だ。Notion はそれではない。

## API レート制限を根本から回避する設計

自分株式会社が採用したアーキテクチャ:

```
Apple HealthKit / Webhook / 外部API
         ↓
  Supabase Edge Function (Deno)
  - バッファリング
  - バッチ処理
  - PostgreSQL直接書き込み
         ↓
  PostgreSQL (無制限書き込み)
         ↓
  Flutter Web (リアルタイム購読)
```

**Supabase の場合のレート制限**:
- Edge Function: 500 req/sec (無料枠)
- PostgreSQL: 接続プール 60 接続 (Pgbouncer)
- Realtime: 接続数 × チャンネル数 = 実質無制限

Notion API の 3 req/sec と比べると **167倍のスループット**。

### 差分: Notion vs PostgreSQL/Supabase

| 項目 | Notion API | Supabase PostgreSQL |
|------|-----------|---------------------|
| 書き込み速度 | 3 req/sec | 数千 insert/sec |
| バッチサイズ | 2000 blocks/req | 制限なし |
| トランザクション | なし | ACID完全対応 |
| インデックス | 固定 | 任意カラム対応 |
| 集計クエリ | 不可 | SQL集計 |
| リアルタイム | なし | Realtime API |

## 「Notion API を使い続けたい」場合の現実的な上限

個人プロジェクトで Notion API を使う際の、現実的な上限:

- **日次バッチ処理のみ** (リアルタイム同期は諦める)
- **1日の書き込み件数 ≤ 100件** (余裕を持って3req/sec × 30秒 = 90req)
- **複雑な横断クエリは諦める** (Notion DB 間の JOINはない)
- **1ページ ≤ 500ブロック** (1000制限の50%を安全マージンに)

この制約内で収まるユースケース: シンプルな日記、週次レビュー記録など。

ライフログ全体を自動化するには不十分だ。

## まとめ

Notion API の 3 req/sec 制限は、チームのドキュメント管理には十分だ。

しかし個人の「全データ統合ライフログ」を自動化しようとすると、すぐに壁にぶつかる。キューイングや差分同期で一時的に回避できても、根本的な解決にはならない。

**本当に必要なのは**: API ではなく、ネイティブに高スループットのデータベースに接続するアーキテクチャだ。
