### はじめに

「自分株式会社」(https://my-web-app-b67f4.web.app/) は Flutter Web + Supabase で構築した個人向け資産・タスク・SNS 管理 SaaS だ。今週は本番環境でしか再現しない2つのバグを修正したので、原因分析から修正内容までを記録する。

どちらも「開発環境では問題なし、本番で初めて気づく」タイプのバグで、再現条件をつかむまでが最も時間がかかった。

---

### 実装方法

#### バグ1: Supabase Edge Function の本番クエリタイムアウト (PR #4058)

**背景**

X (旧 Twitter) の投稿パフォーマンスレポートを生成する `growth-hub` Edge Function が、本番環境で断続的にタイムアウトしていた。ローカルや staging では正常動作。

**原因**

`x_metric_snapshots` テーブルへのクエリがバッチサイズ 50 で走っており、1バッチあたり最大 50 × 1,000 行 = 50,000 行を PostgREST が返そうとしていた。本番の行数・インデックス状態では、この規模のスキャンが production timeout を超えていた。

```typescript
// Before: batchSize = 50 → 1ページ最大 50,000 行スキャン
const batchSize = 50;

// After: batchSize = 10 → 1ページ最大 10,000 行に削減
// 7日分メトリクス × 3時間おき収集 = 56行/投稿 → 10投稿で 560行 < 1,000 行ページ上限
const batchSize = 10;
```

さらに週次レポート用に新関数 `buildXGrowthDataReportContext` を切り出し、不要な historical benchmark データを読まないよう最適化した。旧実装では汎用の `buildXPerformanceContext` を呼んでいたため、レポートが使わないデータまでフルスキャンしていた。

**エラーメッセージの改善**

同時に、エラー発生時のメッセージにコンテキストを付加した。

```typescript
// Before
if (error) throw new Error(error.message);

// After
if (error) throw new Error(`x_metric_snapshots(batch=${batchIndex},page=${page}): ${error.message}`);
```

本番ログで「どのバッチ・どのページでタイムアウトしたか」が即座にわかるようになり、次の問題が起きたときのデバッグ速度が上がる。

**学び**

- PostgREST のデフォルト 1,000 行ページ上限はあくまで *レスポンス* の上限で、DB 側のスキャン量は制限しない。バッチサイズとデータ増加傾向を掛け合わせた最悪ケースを常に計算しておく必要がある。
- 汎用コンテキストビルダーはコード再利用の観点では便利だが、「使わないデータを読む」コストが本番でじわじわ効いてくる。ユースケース特化関数への分割が有効。

#### バグ2: Flutter Web UX デッドエンド修正 — 給料日未設定時の行き止まり (PR #4055)

**背景**

資産管理ページの週次投稿機能で、給料日が未設定のユーザーがトグルをオンにしようとすると SnackBar で `「先に給料日を保存してください」` と表示されてそこで終了、という UX になっていた。

ユーザーにとっては「何をすれば進めるのかわからない状態」で、実際のフィードバックでも「行き止まりになる」という声があった。

**修正内容**

エラーで止めるのではなく、その場で給料日設定ダイアログを開いて、設定が完了したらそのままフローを続行するようにした。

```dart
// Before: エラーを出して終了
if (!_salaryDayConfigured) {
  ScaffoldMessenger.of(context).showSnackBar(
    const SnackBar(content: Text('先に給料日を保存してください')),
  );
  return;
}

// After: 設定ダイアログを開いてから続行
if (!_salaryDayConfigured) {
  await _showSalaryDayDialog();
  if (!mounted) return;
  if (!_salaryDayConfigured) {
    // ダイアログでも未設定のままだった場合のみ中断
    ScaffoldMessenger.of(context).showSnackBar(
      const SnackBar(content: Text('給料日を保存すると週次投稿を有効化できます')),
    );
    return;
  }
}
```

**なぜこれが重要か**

UX の文脈では、ユーザーが次に何をすべきかが明示されない状態を「デッドエンド」と呼ぶ。エラーメッセージは情報を伝えるが、解決への導線がなければユーザーは離脱する。

今回の修正で「設定 → そのまま機能が有効化」という連続したフローが成立し、摩擦がゼロになった。

**学び**

- 「設定が必要です」という案内より「今すぐ設定できます」という体験の方が遥かに完結率が高い。
- `async/await` の前後で `mounted` チェックを忘れると、ダイアログ閉じた後に Widget がアンマウントされていてエラーになる (Flutter あるある)。

### 詰まったポイント

**タイムアウト再現**

本番のみで再現するタイムアウトは、ローカルでは行数が少なく問題が顕在化しない。再現させるためにステージング環境で本番に近い行数を意図的に準備し、バッチサイズを変えながら計測した。最終的に「10投稿分 × 7日 × 3時間おき = 560行」という計算で batchSize=10 が安全域と確認できた。

**`mounted` チェック**

`async/await` を挟む前後では必ず `if (!mounted) return;` を入れるべきだが、既存コードのパターンに倣って省略しがちになる。今回は Dart の linter warning がヒントになった。

---

### まとめ

今週修正した2件はどちらも「本番で初めて気づく」系のバグだった。

- **Supabase Edge Function タイムアウト**: バッチサイズを 50 → 10 に削減し、週次レポート専用コンテキストを切り出して解決
- **Flutter Web UX デッドエンド**: エラーで止める代わりに設定ダイアログを開いて続行、摩擦ゼロのフローを実現

特に前者は、データ量が少ない初期フェーズには問題が出ず、ユーザーが増えてから顕在化するタイプで注意が必要だ。PostgREST を使う際は常に「最悪ケースの行数 × バッチサイズ」を見積もっておくことを強くお勧めする。
