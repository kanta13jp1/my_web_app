### はじめに

個人開発のライフマネジメントアプリ「自分株式会社」（Flutter Web + Supabase）を1人で作り続けている。

今週の最大テーマは「**Claude Code quota超過でも開発を止めない体制づくり**」だ。

AI駆動開発を本格化させるにつれ、Claude Code（Anthropic）に依存しすぎるリスクが顕在化してきた。Maxプランの月次quota上限に達したり、Anthropic APIがダウンしたりすると、開発全体が止まってしまう。この「SPOF（Single Point of Failure）」を解消するために、今週はMulti-AI fallback設計を本格実装した。

---

### 1. なぜMulti-AI Fallbackが必要になったか

#### Claude Code依存の現実

Claude Codeは非常に優秀なAIエージェントだが、個人開発に使い続けると月次使用量の上限（quota）に引っかかることがある。実際に今月、Max planのquota上限に達してしまい、数時間開発が止まるという事態が発生した。

また、Anthropic APIの過去の障害履歴を見ると、平均週1回程度のインシデントが記録されている。「AIがあれば何でもできる」という体制は、裏返せば「AIが落ちたら何もできない」になりうる。

#### 設計目標

- Claude Code token消費量を月50%削減
- 他AIで代替可能なタスク率を70%以上に
- Anthropic API停止時も48時間以内に開発継続可能な体制を確立

---

### 2. タスク別AI振り分け（強制ルーティング）

解決策として、タスクの種類によってAIを振り分ける**強制ルーティングマトリクス**を策定した。

| タスク種別 | Primary AI | Claude Codeの役割 |
|-----------|-----------|----------------|
| 行レベルのコード補完 | **GitHub Copilot** | 不使用 |
| 5分以内の修正 | **Copilot Inline Chat** | 不使用 |
| 500行超のリファクタリング | **Gemini Code Assist** | 事前レビューのみ |
| SQL / アルゴリズム最適化 | **OpenAI Codex** | 仕様確認のみ |
| PR自動レビュー | **Claude API** (Gemini自動fallback) | 不使用 |
| アーキテクチャ判断 | **Claude Code 独占** | 主役 |
| cross-instance-pr作成 | **Claude Code 独占** | 主役 |

Claude Codeは「CEO/アーキテクト専任」と位置づけ、判断・統合・memory管理だけを担当させる。日々の実装は他のAIに分散させることで、Claude quotaの消費を大幅に抑える。

---

### 3. Circuit Breakerパターンの実装

GitHub Actionsのスケジュールタスクにも同様のリスクがあった。Claude APIが落ちたとき、毎時間動いているGHA workflowが全部エラーになる問題だ。

これを解決するためにCircuit Breakerパターンを実装した。

```yaml
# .github/workflows/ci-auto-fix.yml の概念
jobs:
  claude-review:
    steps:
      - name: Claude API circuit breaker check
        id: circuit_check
        run: |
          # 直近1時間のClaude API失敗率を確認
          FAIL_RATE=$(python scripts/check_circuit.py --window 1h)
          if [ "$FAIL_RATE" -gt "50" ]; then
            echo "circuit_open=true" >> $GITHUB_OUTPUT
          fi

      - name: Claude PR review
        if: steps.circuit_check.outputs.circuit_open != 'true'
        run: claude review $PR_NUMBER

      - name: Gemini PR review (fallback)
        if: steps.circuit_check.outputs.circuit_open == 'true'
        run: gemini review $PR_NUMBER
```

Claude APIが不安定な時はGemini 1.5 Flashに自動フォールバックする。これにより、PR自動レビューが24時間365日止まらない体制になった。

### 4. 詰まったポイント

#### (1) Gemini APIの認証切り替え

当初 `GOOGLE_AI_API_KEY` という環境変数名を使っていたが、実際には `GEMINI_API_KEY` が正しいキー名だった。GHA secretsの設定ミスにより、fallbackが発動しなかった問題に気づくまで2時間かかった。

教訓: **環境変数名は公式ドキュメントのサンプルコードで必ず確認する。**

#### (2) 複数インスタンスの並行開発調整

現在、Claude Codeのインスタンスを5つ並行運用している（VSCode版・Windowsアプリ版・PowerShell版・WEB版・スマホ版）。それぞれが同じリポジトリに書き込むため、コンフリクトが頻発していた。

解決策として `docs/cross-instance-prs/` ディレクトリに「他インスタンスへの作業依頼書」を置くルールを整備した。インスタンス間の通信をファイルベースのメッセージパッシングに統一したことで、コンフリクトが激減した。

#### (3) Dart `avoid_dynamic_calls` lint エラー

Windsurf（Codeium社のAIエディタ）が生成したコードに `dynamic` 型の呼び出しが含まれており、CIで `avoid_dynamic_calls` lint エラーが大量発生した。他AIが書いたコードをそのままpushするリスクを実感した。

対策: **他AIが生成したコードは必ず `flutter analyze` を通してからcommitする。**

### 5. 今週の成果まとめ

- AI大学が **152社**に到達（Hume AI・Glean を追加）
- 9本の「デッドEdge Function」をhubに統合し、EF本数が上限50本以内に収まった
- AppLifecycleObserverによるpresence heartbeat制御を実装（タブ非表示時のSupabase接続過多を解消）
- `docs/AI_FALLBACK_RUNBOOK.md` を整備（Claude quota超過時の手順を明文化）

---

### まとめ

「AIがあれば何でもできる」という依存体制は、裏を返すと「AIが落ちたら全滅する」リスクを抱えている。今週の取り組みは、そのリスクを構造的に解消するものだった。

Circuit Breakerパターン、タスク別AI振り分けマトリクス、インスタンス間メッセージパッシングという3つの仕組みを組み合わせることで、Claude quota超過・Anthropic API停止・インスタンス間コンフリクトという3つのリスクを同時に解消できた。

個人開発でここまで複雑な体制が必要かと思われるかもしれないが、「AIを使い倒す」開発スタイルを続けるには避けられない課題だった。同じ悩みを抱える個人開発者の参考になれば幸いだ。
