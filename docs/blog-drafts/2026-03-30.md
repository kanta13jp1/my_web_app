### はじめに

「自分株式会社」は Flutter Web + Supabase で構築している AI 統合ライフマネジメントアプリです。Notion・Slack・MoneyForward など21社の競合 SaaS が持つ機能を1つに統合することを目指して、ひとりで毎日開発を続けています。

2026年3月30日時点で Supabase Edge Function の数が**54本**に到達しました。今回のセッションでは以下を実装しました。

- **notification-center**（アプリ内通知管理・7カテゴリ対応）
- **onboarding-flow**（6ステップの自動オンボーディング）
- **ai-secretary 強化**（12部門の業務知識 + 統計ベース回答）
- **agent-personality / agent-department-manager**（AIエージェントの個性管理）
- **バグ修正4件**（ai-secretary の UPDATE クエリ誤り、growth-achievement-summary の存在しないテーブル参照など）

### 実装方法

#### 1. notification-center Edge Function

通知センターは7カテゴリ（`info`, `warning`, `error`, `success`, `feature`, `system`, `reminder`）に対応した汎用通知管理 API です。

```typescript
// supabase/functions/notification-center/index.ts（抜粋）
const VALID_CATEGORIES = ['info', 'warning', 'error', 'success', 'feature', 'system', 'reminder'];

// エンドポイント設計
// POST /notification-center          → 通知作成
// GET  /notification-center          → 一覧取得（未読のみ or 全件）
// PATCH /notification-center?id=xxx  → 既読マーク
// DELETE /notification-center?id=xxx → 削除
```

DB スキーマは `app_notifications` テーブルで、RLS（Row Level Security）により各ユーザーが自分の通知のみ参照・操作できるようにしています。

```sql
-- migration: 20260330000094_create_notifications_and_onboarding.sql
CREATE TABLE app_notifications (
  id UUID DEFAULT gen_random_uuid() PRIMARY KEY,
  user_id UUID NOT NULL REFERENCES auth.users(id),
  title TEXT NOT NULL,
  body TEXT,
  category TEXT DEFAULT 'info',
  is_read BOOLEAN DEFAULT FALSE,
  created_at TIMESTAMPTZ DEFAULT NOW()
);
ALTER TABLE app_notifications ENABLE ROW LEVEL SECURITY;
```

#### 2. onboarding-flow Edge Function

新規ユーザーの定着率を高めるため、6ステップのオンボーディングフローを実装しました。ステップの完了判定は DB を参照して**自動**で行います。

```typescript
const ONBOARDING_STEPS = [
  { step: 1, title: 'プロフィール設定',   check: () => checkProfileCompleted(userId) },
  { step: 2, title: '最初のノートを作成', check: () => checkFirstNoteCreated(userId) },
  { step: 3, title: 'タスクを登録',       check: () => checkFirstTaskCreated(userId) },
  { step: 4, title: 'AI アシスタントを使う', check: () => checkAiUsed(userId) },
  { step: 5, title: 'チームに参加',       check: () => checkTeamJoined(userId) },
  { step: 6, title: '通知設定',           check: () => checkNotificationSetup(userId) },
];
```

`user_profiles` テーブルに `onboarding_completed` カラムを追加し、全ステップ完了時に `true` をセットします。

#### 3. ai-secretary の12部門強化

AI 秘書が答えられる業務知識を12部門（経営・財務・人事・法務・マーケ・エンジニアリング・CS・営業・総務・広報・購買・IT）に拡張しました。

回答は「統計ベース」になっており、実際の Supabase データ（ユーザー数・タスク数・実績数）を参照した上で、より文脈に沿った返答を生成します。

#### 4. バグ修正のポイント

今回最も時間がかかったのは **ai-secretary の UPDATE クエリ**の修正です。

```typescript
// NG: ORDER + LIMIT を伴う UPDATE は PostgreSQL では非対応
await supabase.from('ai_conversations')
  .update({ reply: aiReply })
  .eq('user_id', userId)
  .order('created_at', { ascending: false })
  .limit(1);  // ← これはエラーになる

// OK: INSERT で別レコードとして保存
await supabase.from('ai_conversations').insert({
  user_id: userId,
  message: userMessage,
  reply: aiReply,
  created_at: new Date().toISOString(),
});
```

Supabase JS クライアントの `.update()` に `.order()` と `.limit()` を組み合わせると実行時エラーになります。同じパターンは他の関数でも踏みがちなので注意が必要です。

### 詰まったポイント

1. **`growth-achievement-summary` が存在しないテーブルを参照していた**
   `referrals` テーブルを参照していたが、実際には存在せず `app_analytics` に統合済みだった。マイグレーション履歴を都度確認する習慣が重要。

2. **Edge Function 数が増えると `edge-function-coverage` のレジストリ更新を忘れがち**
   `coverage/index.ts` 内の関数リストは手動管理なので、新しい関数追加時にセットで更新するルールにした。

3. **RLS ポリシーの順序依存**
   `teams_select` ポリシーは `team_memberships` テーブルの作成後でないと適用できない。マイグレーションファイルの番号（実行順）に注意。
