### はじめに

Flutter Webで作ったWebアプリ「自分株式会社」(https://my-web-app-b67f4.web.app/) が、長らくGoogleにまともにインデックスされていなかった。

SPAの宿命とも言えるSEO問題だ。Javascriptが実行されないと正確なコンテンツが取れない→Googlebotがクロールしてもblankに近いHTMLしか拾えない→インデックス品質が低い→検索流入ゼロ、という負のループ。

2026年7月の1週間で、この問題を正面突破した。具体的には以下の3本柱を実装した:

1. **/vs-\* 比較ページの静的HTML事前生成 (30社)**
2. **主要8公開ルートのprerender拡張**
3. **Organization/WebSite/Article JSON-LD構造化データの全ページ適用**

---

### 実装方法

#### 1. /vs-\* 比較ページ — Flutter WebのSEO最重要レバー

競合他社との比較ページ (/vs-notion、/vs-slack など30社分) を、ビルド時に静的HTMLとして事前生成するスクリプトを作成した。

```
scripts/prerender_seo_routes.py
web/seo/comparison-routes.json
```

**ポイント**: Firebase Hostingは、静的ファイルが存在する場合、`firebase.json`のrewrite設定よりも**静的ファイルを優先して配信**する。つまり、`/vs-notion.html`というファイルをpublicディレクトリに置くだけで、Googlebotは完全なHTMLを受け取れる。Flutter Webのroutingには一切変更不要。

生成される静的HTMLの構成:
- `<title>` と `<meta description>` を競合名ごとに固有化
- `<link rel="canonical">` を自己参照で設定
- Article型JSON-LDを埋め込み
- クロール可能な本文 (各社の特徴比較テキスト) を配置

**sitemapの大手術**: 実装前は1990 URLが登録されていたが、大半が動的パスで品質が低かった。今回47 URLに刈り込み。「少ないが高品質なURL」の方がクロールバジェットを有効活用できる。

#### 2. 主要8公開ルートのprerender拡張

ランディングページ・機能紹介・料金ページ等、訪問者が最初に目にする8ルートを同スクリプトでprerender化した。

各ルートごとに固有の:
- H1/H2/H4 見出し構造
- JSON-LD (WebPage/WebApplication型)
- OGP meta tags

を持つ静的HTMLを生成。GHA deploy時に自動実行される。

また、英語H2見出しを「高需要日本語キーワード」に変換した。例: "Features" → "自分株式会社の特徴・機能一覧"。日本語検索ユーザーへの可視性を高める地道だが効果的な施策。

#### 3. 構造化データ (JSON-LD) の強化

`dd2d1e4` のコミットで、Organization・WebSite・Article型のJSON-LDをすべての公開ページに適用した。

```json
{
  "@type": "Organization",
  "name": "自分株式会社",
  "url": "https://my-web-app-b67f4.web.app/",
  "@type": "WebSite",
  "potentialAction": {
    "@type": "SearchAction",
    "target": "https://my-web-app-b67f4.web.app/search?q={search_term_string}"
  }
}
```

合わせて `trailingSlash: false` 設定を追加し、`/vs-notion` と `/vs-notion/` が重複インデックスされる問題を防いだ。

### 詰まったポイント

**① Firebase rewriteとの競合**

最初、静的HTMLを生成してもFlutterのindex.htmlにフォールバックしてしまっていた。原因は`firebase.json`のrewrite設定の順序。静的ファイルはrewriteの評価前に提供されるはずなのに、キャッシュや設定ミスで意図どおり動かないケースがあった。

解決策: `hosting.cleanUrls: true` と静的ファイルのパス命名規則を統一することで解消。

**② sitemapの1990→47削減の判断**

「URLが多い=SEOに有利」という誤解が初期設計にあった。実際は:
- 動的に生成されたURLでコンテンツが薄い → Googleが「低品質ページ」と判断
- クロールバジェットが低品質ページに消費される → 重要ページへのクロールが遅れる

Google Search Consoleの「インデックス登録済み」と「クロール済みだがインデックス未登録」の比率を見て、思い切って1943 URLを削除した。

**③ Flutter Webでのcanonical URL管理**

Flutter WebはSPA。`index.html` が単一ファイルなので、canonicalをページごとに動的に変えるにはJS操作が必要。prerender時にそれぞれ別ファイルとして生成することで、**静的canonicalを各ページに持たせる**アプローチが正解だった。

### まとめ

今週の実装で、Flutter WebのSEO課題に対するひとつの解答が出せた:

| 手法 | 効果 |
|------|------|
| /vs-\* 静的HTML化 | Googlebotが完全なコンテンツを取得可能に |
| prerender拡張 | 主要8ルートのインデックス品質向上 |
| JSON-LD強化 | リッチリザルト表示の対象に |
| sitemap精査 | クロールバジェットの最適化 |

Flutter Webは「SEOが弱い」と言われるが、適切なprerender戦略と静的ファイル生成を組み合わせれば、通常のSSRフレームワークと同等以上のSEO品質を実現できる。
