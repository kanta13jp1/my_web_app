# dev.to 100本投稿記念 — 個人開発ブログを続けて学んだ10のこと

dev.to に 100本投稿した。Flutter / Supabase / AI / 個人開発の技術記事を書き続けた結果、予想外の学びが多かった。

## 100本の内訳

```
技術カテゴリ別:
  Flutter:        22本 (状態管理/アニメーション/テスト/Web最適化)
  Supabase:       18本 (Auth/RLS/Realtime/Edge Functions)
  AI/LLM:         20本 (Claude API/プロンプト設計/エージェント)
  個人開発:        25本 (KPI/SEO/コスト/マーケティング)
  GHA/自動化:     15本 (CI/CD/スケジュール/セキュリティ)

言語:
  英語 (EN):      50本 (dev.to 国際向け)
  日本語 (JA):    50本 (Qiita/note 向け下書き)
```

## 学んだ10のこと

### 1. 「完璧な記事」より「公開した記事」

最初の10本は下書きのまま眠っていた。「まだ不完全だ」「もっと調べてから」という罠。100本書いた今振り返ると、質は書き続けた量と正比例した。

### 2. 実装と同時に書くと速い

```
悪いパターン:
  実装 → 動いた → 後で記事にしよう → 3週間後に書けなくなる

良いパターン:
  実装しながら記事を書く →
  つまずいた箇所がそのまま記事の「課題」セクションになる
```

### 3. コードブロックが読まれる

アクセス解析をすると、コードブロックのある記事が2倍以上読まれる。「なんとなく書いた Flutter の実装例」が予想外に伸びた。

### 4. タイトルに具体数字を入れると CTR 上がる

```
❌ 「Flutter 状態管理の比較」
✅ 「Flutter 状態管理比較 — Provider / Riverpod / Bloc の選び方」

❌ 「個人開発のコスト削減」
✅ 「個人開発のコスト管理 — $0から$100/月のスタック設計」
```

### 5. 英語記事は海外エンジニアから反応が来る

dev.to の英語記事は予想以上に読まれた。日本語記事の5倍以上のインプレッション。英語は苦手でも「コードで伝わる」技術記事は特にハードルが低い。

### 6. 失敗談が最もシェアされる

「失敗から学んだ10のこと」「3つの製品が失敗した理由」系の記事が、成功事例の記事より多くシェアされた。失敗談は読者の「あるある」を刺激する。

### 7. GHA 自動化で「書く習慣」が維持できた

```yaml
# 週次で下書きの状況を確認するリマインダー
on:
  schedule:
    - cron: '0 9 * * MON'
jobs:
  blog-reminder:
    steps:
      - run: |
          COUNT=$(find docs/blog-drafts -name "*-en.md" \
            | xargs grep -l "^published: false" | wc -l)
          echo "未投稿の下書き: $COUNT 本"
```

下書きが溜まると自動でリマインドされる仕組みを作ったことで、「忙しくて更新できない」期間が減った。

### 8. タグは慎重に (dev.to は 4つまで有効)

dev.to は frontmatter の `tags:` が 5 個以上あっても先頭4個しか適用されない。具体的なタグ (flutter, supabase) を汎用タグ (webdev, programming) より前に置く。

### 9. 連載シリーズは継続率を高める

単発記事より「Phase X シリーズ」形式で書くと継続しやすかった。「次は何を書くか」の決断コストがゼロになるため。

### 10. 書くことで理解が深まる

「分かった気がしていた」技術を記事にしようとすると「分かっていなかった部分」が浮き彫りになった。特に Supabase RLS と Claude API のコスト最適化は、記事を書くまで曖昧に理解していた。
