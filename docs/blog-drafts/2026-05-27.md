## 本文下書き

### はじめに

個人開発で AI ツール（Claude Code、Codex、Cursor など）をフル活用するとき、**「ツール自体の更新を追いきれない」** 問題が出てきた。

Claude Code だけでも週に 1〜3 回アップデートがある。Codex CLI も同様だ。新しい機能や破壊的変更を見逃すと、自分が構築したワークフロー自体がいつの間にか非推奨になっている。

「自分株式会社」(https://my-web-app-b67f4.web.app/) では Flutter Web × Supabase で個人財務・生産性アプリを開発しているが、今週は **AI ツール監視システム「ai-tool-watch」** の稼働報告と、**2026-05-27 に検知した Claude Code 2.1.152 / Codex CLI 0.134.0 のアップデート** をワークフローに取り込む話をまとめる。

### 実装方法

#### 1. ai-tool-watch — 毎日自動で公式ソースを監視する仕組み

`scripts/ai_tool_watch.py` は GitHub Actions の daily cron で実行される。監視対象は 8 つの公式ソース：

```
Claude Code changelog  → code.claude.com/docs/en/changelog
Claude Code hooks ref  → code.claude.com/docs/en/hooks
Codex changelog        → developers.openai.com/codex/changelog
Codex use cases        → developers.openai.com/codex/use-cases/
Cursor changelog       → cursor.com/changelog
Gemini Code Assist     → developers.google.com/gemini-code-assist/...
Devin release notes    → docs.devin.ai/release-notes
(Copilot, Windsurf, etc.)
```

各ソースの「最新シグナル」（バージョン文字列 or ページの冒頭数百文字）を前回分と diff し、変化があれば `docs/ai-tool-watch/latest-report.md` に更新して commit / push する。変更があった場合はさらに `ai_tool_watch_route.py` がルーティングを実行し、**どの instance（Claude Code #1 か Codex #1）に何をやらせるか** の handoff ファイルを自動生成する。

#### 2. 今週の検知内容 — Claude Code 2.1.152 & Codex CLI 0.134.0

2026-05-27 の実行で以下の変更を検知した：

| ツール | バージョン | 主な変更 |
|---|---|---|
| Claude Code | 2.1.152 | Hooks reference 更新 |
| Codex CLI | 0.134.0 pre | `--profile` フラグを全 CLI・TUI・sandbox flow で統一 |
| Cursor | 3.5 | `/loop` skill 追加（ローカルスケジュールで繰り返し実行） |
| Gemini Code Assist | 2.82.0 | agent mode 移行完了（旧ツール廃止） |

Claude Code の Hooks 更新は当社ワークフローへの影響が大きい。現在 `SessionStart` / `UserPromptSubmit` / `PostToolUse` / `Stop` の 4 フックを使って **セッションコンテキスト注入・lint-test フィードバック・memory 蓄積** を自動化しているため、仕様変更があればすぐに対応が必要だ。

Codex CLI の `--profile` 統一は、当社の 2-instance fleet における **プロファイル管理の簡素化** に直結する。

#### 3. 2-instance fleet へのルーティング設計

ai-tool-watch が変更を検知すると、`routing_groups`（`hooks`, `codex-runtime`, `schedule`, `integration`, `quality-cost`）に基づいて担当 instance を決める：

```
Claude Code #1 → hooks / architecture / review / cross-instance 調整
Codex #1       → scoped 実装 / CI repair / Edge Functions / GHA / broad scan
```

今回の Claude Code 2.1.152 変更は `hooks` グループに該当するため **Codex #1** にルーティングされた。理由は「hooks の仕様変更を実際のスクリプトに反映する作業はスコープが明確で、Codex #1 のクリーン worktree で安全に実行できる」からだ。

#### 4. Prompt Caching × Opus 4.7 — 88% コスト削減の実績

2-instance fleet を Opus 4.7 で回すと **キャッシュなしでは月 $15,000 超** になる計算だ。

```
2 instance × 50 turn/日 × 1M context × $6.25/Mtok × 25 日 = $15,625/月
```

実際には `CLAUDE.md` + `docs/` をキャッシュ可能な安定ブロックとして設計し、5 分 ephemeral キャッシュを活用することで：

```
初回 write: $7.81/Mtok（1.25倍）
以降 read : $0.625/Mtok（0.1倍 = 90% OFF）
break-even: 11.5 hit で元が取れる
```

1 セッション 50 ターンで試算すると **$38/日（88% 削減）** に収まる。月 $20 プランの制限内で 2 instance を安全運用できている。

### 詰まったポイント

**ルーティングの「意図の明示化」が難しい**

ai-tool-watch のルーティングは keyword ベースで行っているが、「hooks の変更」が Claude Code #1 と Codex #1 のどちらに行くべきかは文脈によって変わる。現在は **変更の実装コスト（architecture 判断が必要か？スコープが明確か？）** で分岐させているが、このロジック自体を定期的に見直す必要がある。

**キャッシュ TTL の選択**

5 分 ephemeral vs 1 時間 cache の使い分けは、セッションの中断頻度によって最適解が変わる。1 時間 cache は write 単価が 2 倍だが、中断を挟む長時間セッションでは break-even を下回る。現在は「連続開発は 5 分 / wrap-up 挟む場合は 1 時間」をルールにしている。

**自動化の「盲点」**

daily cron で全ソースを監視しているが、**公式 changelog に載る前に破壊的変更が入ることがある**（npm publish → docs 更新のラグ）。これを補うために `@anthropic-ai/sdk` と `@openai/codex` の npm registry も追加監視対象にする予定だ。

### まとめ

今週の核心は「**ツールの更新を人手で追うのをやめる**」という意思決定だ。

ai-tool-watch → routing → handoff の pipeline が動くことで、「Claude Code が更新されたので今日のセッションで反映しよう」という判断を AI が自動化してくれる。人間がやるべきことは **routing の正しさを週次で検証すること** だけになった。

Prompt Caching によるコスト制御と合わせて、**個人開発でも 2-instance の AI fleet を月 $20 以内で運用できる** 設計が整ってきた。
