### はじめに

「自分株式会社」はFlutter Web + Supabase Edge Functions (Deno) で構築したAI統合ライフマネジメントアプリです。Notion・Slack・MoneyForwardなど21社の競合機能を1つに集約しているため、ホーム画面を表示する際に複数テーブルへの問い合わせが同時に発生します。

開発初期は実装の素直さを優先し、クエリを1件ずつ順番に実行するコードを書いていました。しかし機能が増えるにつれて `app-analytics-dashboard` では9クエリ、`blog-post-manager` では14クエリが逐次実行されるようになり、レスポンスタイムが目に見えて悪化してきました。

今回は直近1週間で実施した **「逐次クエリ → Promise.all 並列化」** リファクタリングの実例を紹介します。同じ構成 (Deno + Supabase JS クライアント) を使っている方にそのまま応用できる内容です。

---

### なぜ逐次実行が遅いのか

Supabase Edge Functions は Deno ランタイム上で動き、各クエリは非同期 (Promise) として実行されます。`await` を毎回挟んで逐次実行すると、クエリ間に不要な待ち時間が生まれます。

```typescript
// 悪い例: 3クエリを逐次実行
const users = await supabase.from('user_profiles').select('count');
const events = await supabase.from('signup_events').select('count');
const referrals = await supabase.from('referral_events').select('count');
```

上記は「usersが終わってからeventsを取得」→「eventsが終わってからreferralsを取得」という直列処理になります。それぞれ独立したテーブルに対するクエリなので、本来は同時に投げられます。

---

### 実例1: user-growth-analytics — 3クエリ並列化

`user-growth-analytics` の `overview` アクションでは、ユーザー一覧・サインアップイベント・リファラルイベントの3クエリが逐次実行されていました。

**Before (逐次)**
```typescript
const usersResult = await supabase.auth.admin.listUsers();
const signupResult = await supabase.from('signup_events').select('*');
const referralResult = await supabase.from('referral_events').select('*');
```

**After (Promise.all 並列)**
```typescript
const now = new Date();
const todayStart = new Date(now.getFullYear(), now.getMonth(), now.getDate()).toISOString();
const weekStart = new Date(now.getTime() - 7 * 86400000).toISOString();

const [usersResult, signupResult, referralResult] = await Promise.all([
  supabase.auth.admin.listUsers(),
  supabase.from('signup_events').select('*').gte('created_at', todayStart),
  supabase.from('referral_events').select('*').gte('created_at', weekStart),
]);
```

ポイントは「時刻境界 (`todayStart` / `weekStart`) を事前に計算してから全クエリを並列起動する」こと。`listUsers()` の完了を待たずに3本のクエリが同時に走ります。

### 実例2: app-analytics-dashboard — 9クエリ全並列化

KPI概要ビューでは7テーブルのカウントクエリに加え、`recentUsers` と `funcStatus` が別段階で取得されていました。これを1段の `Promise.all` に統合しました。

```typescript
// Before: 3段逐次 (7並列 → await → 1クエリ → await → 1クエリ)
const counts = await Promise.all([/* 7クエリ */]);
const recentUsers = await supabase.from('user_profiles').select('id,email,created_at')...;
const funcStatus = await supabase.from('edge_function_ui_status').select('*');

// After: 1段並列 (9クエリ同時)
const [userCount, noteCount, taskCount, goalCount,
       habitCount, requestCount, achievementCount,
       recentUsers, funcStatus] = await Promise.all([
  supabase.from('user_profiles').select('*', { count: 'exact', head: true }),
  supabase.from('notes').select('*', { count: 'exact', head: true }),
  supabase.from('tasks').select('*', { count: 'exact', head: true }),
  supabase.from('goals').select('*', { count: 'exact', head: true }),
  supabase.from('habits').select('*', { count: 'exact', head: true }),
  supabase.from('feature_requests').select('*', { count: 'exact', head: true }),
  supabase.from('development_achievements').select('*', { count: 'exact', head: true }),
  supabase.from('user_profiles').select('id,email,created_at').order('created_at', { ascending: false }).limit(10),
  supabase.from('edge_function_ui_status').select('*').order('function_name'),
]);
```

逐次3段→1段。ラウンドトリップ数が大幅に減少します。

### 実例3: blog-post-manager — 14クエリ逐次を3段並列に

最も大きな改善でした。ブログ投稿管理画面では:
- メインリスト取得 (1クエリ)
- 11プラットフォーム別の投稿数カウント (11クエリ)
- 今日の投稿数 (1クエリ)
- ドラフト数 (1クエリ)

合計14クエリが逐次実行されていました。これを次の3段構成に変更しました。

```typescript
// 段1: メインリスト + 今日の日付計算
const todayStr = new Date().toISOString().slice(0, 10);

// 段2: リスト取得 + 全プラットフォームカウント + 今日の投稿数を並列
const [postsResult, ...platformCounts] = await Promise.all([
  postsQuery, // フィルタ済みリスト
  ...PLATFORMS.map(p =>
    supabase.from('blog_posts')
      .select('*', { count: 'exact', head: true })
      .contains('target_platforms', [p])
  ),
  supabase.from('blog_posts').select('*', { count: 'exact', head: true })
    .gte('created_at', todayStr),
]);
```

14クエリ逐次 → 実質1ラウンドトリップ相当に。

### 詰まったポイント

**1. エラーハンドリングの漏れ**

`Promise.all` は1つでも reject されると全体が失敗します。Supabase JS クライアントは通常 `{ data, error }` を返すので reject はしませんが、`supabase.auth.admin.listUsers()` はエラー時に throw する場合があります。`try/catch` で全体を囲むか、個別にエラーチェックすることが重要です。

```typescript
const [usersResult, signupResult] = await Promise.all([...]).catch(err => {
  throw new Error(`並列クエリ失敗: ${err.message}`);
});
if (usersResult.error) throw usersResult.error;
```

**2. deno lint の警告**

Optional chain (`?.`) を多用していた箇所が `deno lint` で `no-extra-non-null-assertion` 警告を出すことがありました。`Promise.all` の結果を destructure する場合は型が明確になるため、むしろ `?.` を外して明示的な `?? []` に統一する方が型安全です。

**3. 依存関係のあるクエリは並列化できない**

「ユーザーIDを取得してから、そのIDで詳細を引く」といった直列依存があるクエリは当然並列化できません。独立しているクエリを見極めることが第一歩です。

### まとめ

Deno (Supabase Edge Functions) での `Promise.all` 並列化は、実装コストが低い割に効果が大きいパフォーマンス改善手法です。今回の実装で学んだポイントをまとめます:

- **独立したクエリはすべて並列化**する。テーブルをまたぐカウントは最たる候補
- **事前計算できる変数 (日付境界など) は `Promise.all` の外で計算** してから並列起動
- **エラーハンドリングは `Promise.all` の外で統一的に** 行う
- **deno lint 0件を維持** — 並列化後は型チェックが厳しくなる箇所が出やすい

今後はクエリのキャッシュ戦略 (Supabase の Row Level Security と組み合わせた edge-side cache) にも取り組む予定です。
