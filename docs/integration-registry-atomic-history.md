# 外部システム定義の原子的バージョン管理（#1237）

## 契約

`enterprise-hub` は認証済み利用者IDと検証した入力を
`insert_integration_registry_version` に渡す。クライアントで版番号を決めない。
RPCが未配備・失敗の場合、直接INSERTにフォールバックしない。

RPCは `SECURITY INVOKER` で実行し、`service_role` だけに実行権限を付与する。
公開・認証済みクライアントの実行権限は取り消す。入力metadataの所有者と
versionは、サーバーから渡された利用者IDとDB側の採番結果で上書きする。
利用者IDの認証は呼び出し元Edge Functionの責任であり、RPCのパラメータだけを
信頼して公開クライアントへRPCを開放してはならない。

所有者・種別・キー単位のトランザクションアドバイザリロック取得後に、
履歴の最大版番号を読み、次の行を保存する。ロックはcommit/rollbackで解放される。
ハッシュ衝突は別キーの待ち時間を増やすだけで、同一性判定や所有権を変えない。
部分一意インデックスを最終防御とし、READ COMMITTED以外の競合や直接の
サービスロール書き込みでも重複版番号を成功させない。

対象は `integration_registry_system` / `integration_registry_interface` /
`integration_registry_mapping` のみ。対象履歴のUPDATE/DELETEおよび別種別から
対象種別へのUPDATEを拒否する。他種別の権限・RLSは変更しない。

## 移行と失敗時の運用

移行は単一トランザクション。既存履歴の所有者・キー・版番号が不正、または
版番号が重複していれば制約／一意インデックス作成に失敗して全体を戻す。
正常な履歴行は更新せず、既存の最大版番号から続ける。版番号は1～999999999。
上限到達時も既存履歴を変更せず失敗する。
移行中のロック待ちは5秒、各SQL文の実行は60秒で打ち切る。
タイムアウトも移行失敗として扱い、負荷・実行計画・配備時間帯を確認する。

失敗時に制約を弱めたり、履歴を自動再採番・削除してはならない。
本番反映を止め、原因・影響件数と人による回復方針をIssueへ記録する。
秘密情報や履歴本文をログへ出力しない。移行前に検証済みバックアップと
復元手順を確認し、移行→Edge Function更新の順に配備する。
履歴変更を必要とする将来の管理操作も、別の明示承認と検証を必要とする。

## 決定的検証

GitHub Actions `Integration registry atomic history` は本番秘密情報を使用せず、
隔離されたPostgreSQL 17で `scripts/registry_atomic_test.py` を実行する。
このスクリプトは専用の空DBとロールを作るため、本番・共有DBで実行しない。

- 3種別各24件の並行書き込みが連続・一意の版番号になること。
- 1件目のトランザクションを開いたまま2件目の未取得アドバイザリロックを
  `pg_locks` で確認し、1件目のcommit後に版番号1・2で成功すること。
- 別所有者の独立採番とRLSによる読取分離。
- metadataの所有者／版番号偽装が採用されないこと。
- RPCと直接INSERT、種別変更による認証済みクライアントの迂回を拒否すること。
- 重複INSERT、履歴UPDATE/DELETEを拒否し、他種別のCRUDは維持すること。
- 正常履歴の保持と採番継続、重複・不正履歴による移行全体のロールバック。
- 保存失敗で行が残らず、ロック解放後の再実行が成功すること。

この隔離テストだけで本番履歴の健全性・全体のSupabase設定・実ユーザーの
受け入れを証明したとはしない。通常のPR CI、最終差分レビュー、本番移行結果と
認証済み機能確認が揃ってからIssueを完了する。
