# Jwenv 支出カテゴリ判定方式の見直し（事前登録）

2026-09-25 作成。この文書と `web/labs/jwenv/holdout.json` は、方式Bを一度も実行していない時点でコミットする。結果を見た後に、しきい値・プロンプト・検証用メモ・参照カテゴリを変えない。変えた場合は別の方式として記録し直す。

## 背景

方式Aの実測（run 35694974350、SwiftShader、元の14件）では、参照のある11件中10件が参照と一致した。一方、12問のP(yes)が多くのカテゴリで0.8前後に並び、情報が足りない「支払い」でも最大値が0.8360だった。「最大P(yes)が0.5未満なら要確認」という基準では、要確認として作った3件を1件も拾えなかった。

## 方式A（比較用。変更しない）

1. 12カテゴリそれぞれについて、`noul` の質問「{領域}として、この支出は「{ラベル}」（{説明}）に当てはまりますか？」を作り、12問を1回の `systemOne` で実行する。
2. P(yes)が最大のカテゴリを候補にする。
3. 最大P(yes)が0.5未満なら要確認にする。

## 方式B（二段階。今回の提案）

1. 段階1は方式Aの1と同じ（同じ要求の結果を共有する）。
2. 段階2：P(yes)の上位8カテゴリを選択肢にした `choice` を1問作り、`options.permutations: 8` で実行する。
   - 指示文：「{領域}として、この支出に最も当てはまるカテゴリを選んでください」
   - 選択肢の説明：「{ラベル}（{説明}）」
   - 並べ順は段階1の順位の順。8通りの回転を平均することで、段階1の順位とラベル位置（A〜H）の結び付きを打ち消す。
3. 段階2の `choice` を候補にする。
4. 段階2で候補の確率が0.5未満（過半数に届かない）なら要確認にする。

理由：`noul` のP(yes)は質問ごとに独立で、カテゴリ同士を比べる尺度になっていない。段階2は `choice` なので、確率の合計が1になり、「他の候補すべてを合わせたより高いか」で判断できる。選択肢が8個までに限られるため、段階1で絞り込む。

## 評価

データ：

- 元の14件（参照11件、要確認3件）。方式Aの結果はすでに見ているため「既知」として分けて報告する。
- 検証用の20件（`holdout.json`。参照12件、要確認8件）。この文書と同時にコミットし、方式A・Bとも未実行。

指標（それぞれ元の14件と検証用20件に分けて報告）：

1. 要確認メモ（参照なし）のうち、要確認と判定した件数（主指標）
2. 参照のあるメモのうち、候補が参照と一致した件数
3. 参照のあるメモのうち、誤って要確認にした件数
4. 方式Bで、参照カテゴリが段階1の上位8に入った件数
5. 段階1・段階2それぞれの要求時間（環境ごと）

事前に決める判断基準：検証用20件で、方式Bが方式Aより多くの要確認メモを拾い、かつ参照一致が方式Aより2件以上減らなければ「方式Bを採用候補にする」。満たさなければ、方式Bは不採用として記録する。件数が少ないため、どちらの場合も一般的な精度は主張しない。
