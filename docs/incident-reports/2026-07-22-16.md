## 2. 🔴 障害A: cs-check のキャッシュ更新が 82 日間失敗し続けている (緑のまま)

### 事象

`cs-check.yml` は 2 時間ごとに成功しているが、**その成果物である 2 ファイルが 3 ヶ月近く更新されていない**。

| ファイル | 最終更新 commit | 経過 |
|----------|----------------|------|
| `docs/ticket-cache.json` | `88794b6e1` 2026-05-01 15:29:47 UTC | **82 日** |
| `docs/flutter-analyze-cache.json` | `cb81250a9` 2026-04-30 03:20:11 UTC | **83 日** |

直近 8 run はすべて `success` (最新 2026-07-22T14:18Z)。

### 根本原因

run `29927923656` のログに実際の失敗が出ている:

```
gh: Could not update file: 2 of 2 required status checks are expected. (HTTP 409)
⚠️ docs/ticket-cache.json 更新失敗
gh: Could not update file: 2 of 2 required status checks are expected. (HTTP 409)
⚠️ docs/flutter-analyze-cache.json 更新失敗
✅ GitHub API ファイル更新完了      ← 無条件に出力される
```

`.github/workflows/cs-check.yml` の `update_file()`:

```bash
gh api -X PUT "repos/${REPO}/contents/${path}" \
  --input - <<< "$body" --silent && \
  echo "✅ $path 更新完了" || echo "⚠️ $path 更新失敗"
```

`|| echo` が **失敗を握り潰して step の exit code を 0 にする**。加えて step 末尾の
`echo "✅ GitHub API ファイル更新完了"` が無条件実行されるため、ログの最終行だけ見ると成功に見える。

step 名は「**branch protection bypass**」だが、main に required status checks (2件) が
設定された時点でこの Contents API 直書き経路は 409 で恒久的に塞がれている。
bypass が壊れたこと自体は誰にも通知されなかった。

### 影響

1. `docs/cs-check-web.md` は WEB版 sandbox の代替手順として
   「`cat docs/ticket-cache.json`」「`cat docs/flutter-analyze-cache.json`」で
   インフラ/CI 状態を読めと指示している。**この 2 ファイルは 4〜5 月のデータを現在値として提示する**。
2. とくに `flutter-analyze-cache.json` は
   `analyze_ok: false` / `conclusion: "cancelled"` / `head_sha: 9bde2d17` (2026-04-11) で固定されており、
   **実在しない CI 赤を 3 ヶ月間表示し続けている**。
3. 同じ `update_file()` を CS ノート (`docs/cs-notes/<datetime>.md`) の書き込みにも使っている。
   つまり **cs-check が異常を検知したときの報告経路も同時に死んでいる** —
   異常が起きても記録が残らない。

### 対応案 (未実施 / 要レビュー)

- `update_file()` の失敗を集約し、1 件でも失敗したら step を非ゼロ終了させる (最優先。まず可視化する)。
- 書き込み経路を Contents API 直書きから、他の自動化と同じ **branch → PR** 方式へ変更する。
- あるいはキャッシュを git 管理から外し、Actions artifact / Supabase テーブルへ退避する
  (毎時 commit を main に積む設計自体が branch protection と本質的に相性が悪い)。

## 3. 🔴 障害B: cs-check の Supabase 死活監視が存在しない EF を叩いており、404 を healthy と判定

### 事象

同じ run のログ:

```
🔍 Supabase: HTTP 404
```

`cs-check.yml` Step 5 が叩いているのは `functions/v1/development-achievements`。
実測でも 404 で、**`supabase/functions/` 配下に origin/main 時点で存在しない**
(比較: `functions/v1/health-check` は 200)。

### 根本原因

判定の閾値がこうなっている:

```bash
if [ "$SUPABASE_CODE" -ge 500 ] 2>/dev/null || [ "$SUPABASE_CODE" = "000" ] || [ "$SUPABASE_CODE" = "403" ]; then
```

**404 がアラート集合に入っていない**。よって「監視対象の Edge Function が消滅している」
という最も分かりやすい異常が `healthy=true` として通過する。
この probe は Supabase Functions が全滅して全て 404 を返しても緑を出す = 死活監視として無意味。

### 対応案 (未実施 / 要レビュー)

- probe 先を実在する `functions/v1/health-check` に変更し、返却 JSON の `status` フィールドまで検証する
  (HTTP コードだけでなく本文を見る)。
- 判定を許可リスト方式へ反転する: `[ "$CODE" != "200" ]` を異常とする。
  現行の「特定コードだけ異常」方式が今回の穴を作った。
