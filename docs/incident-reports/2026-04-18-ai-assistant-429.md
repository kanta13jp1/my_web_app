# インシデントレポート: ai-assistant 429 Too Many Requests (2026-04-18)

## 発生状況

- **日時**: 2026-04-18 01:30 JST 頃
- **症状**: Web アプリ (<https://my-web-app-b67f4.web.app/>) で AI 呼び出し時に連続エラー
  - `POST /functions/v1/ai-assistant 400 (Bad Request)`
  - `POST /functions/v1/ai-assistant 429 (Too Many Requests)` (同一セッション内連続)
- **影響範囲**: AI 秘書・AI プレゼン作成・予算プランナー等 17+ ページ
- **関連ログ**: ブラウザ console (Fetch failed loading POST ...)

## 原因分析

`supabase/functions/ai-assistant/index.ts:854` の catch ブロックで、上流 API
(OpenAI / Anthropic / Gemini) から `quota` / `rate limit` メッセージを検知したら
**429** を返す実装になっている:

```ts
const isQuotaError = /quota|rate limit/i.test(msg);
const status = isQuotaError ? 429 : 400;
```

そのため 429 は「上流プロバイダーの API キーが quota 枯渇している」サインである。
400 は他の一般的なエラー (モデル応答解析失敗等)。

## Flutter 側の緩和策 (Windowsアプリ版#77 で実装済み)

**`AiQuotaGuard` サーキットブレイカーを [lib/services/ai_service.dart](../../lib/services/ai_service.dart) に追加**:

- 429 を検知すると 60 秒間の cooldown を開始
- cooldown 中の `AIService` 呼び出しは即座に `AIServiceException(errorType: RATE_LIMIT)` を throw
- 上流 API への無駄な連打を防止
- UI 側は `isRateLimitError` で分岐して「残り N 秒」を表示可能

**制約**: `_supabase.functions.invoke('ai-assistant', ...)` を直接呼び出している
17+ ページ (AiService 未経由) は guard を通らない。リファクタ要。

## ユーザー (管理者) 側で要確認

### 1. Supabase Secrets の API キー残高確認

Supabase Dashboard → Project Settings → Edge Functions → Secrets で以下を確認:

| シークレット | 確認先 | 対処 |
| --- | --- | --- |
| `OPENAI_API_KEY` | <https://platform.openai.com/usage> | 使用量 / 課金プラン確認 |
| `ANTHROPIC_API_KEY` | <https://console.anthropic.com/settings/usage> | Claude API 残高 |
| `GEMINI_API_KEY` | <https://aistudio.google.com/apikey> | 無料枠リセット確認 |
| `DEEPSEEK_API_KEY` | <https://platform.deepseek.com/> | 残高確認 |
| `XAI_API_KEY` | <https://console.x.ai/> | Grok 残高 |

### 2. `ai_quota_usage` テーブル確認

```bash
# Supabase CLI または REST API
curl -s -H "apikey: $SUPABASE_SERVICE_KEY" \
  "https://smmkxxavexumewbfaqpy.supabase.co/rest/v1/ai_quota_usage?order=created_at.desc&limit=20"
```

直近 24 時間の provider 別使用量を確認し、特定のプロバイダーが枯渇していないか見る。

### 3. `quota-monitor.yml` ワークフロー最新ラン確認

```bash
gh run list --workflow=quota-monitor.yml --limit 5
gh run view <run-id> --log
```

本インシデント対応で `2026-04-18 16:51 UTC` にディスパッチ済み
(run ID: `24576623713`)。成功していれば最新データが Issue コメントに投稿される。

### 4. フォールバック戦略の実装検討

一つの provider が枯渇したら他プロバイダーへ自動切替:

- `ai-assistant/index.ts` の `runFallbackChain` で quota エラーを検知 → 次の provider へ
- 現状は上流エラーが全 provider 共通で起きる (全滅) とチェインが機能しない
- 中長期: OpenRouter / Together AI / Fireworks 等の **複数プロバイダー統合層** への移行
