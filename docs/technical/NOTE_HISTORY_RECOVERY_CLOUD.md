# Note history recovery: real Storage sandbox

Status: implementation prerequisite, not a completed application restoration feature.

The history/Task hierarchy contract uses a minimal PostgreSQL fixture with
stubbed base import/verify functions. It proves those SQL contracts, but does
not prove attachment byte recovery through the real Storage service.

The cloud-only sandbox starts isolated Auth/Postgres/Storage on a GitHub-hosted
runner. It never links a project, loads production configuration, receives
repository secrets, copies ENEX, or contacts an external data endpoint.
The CLI release and downloaded binary SHA-256 are pinned. A CLI-created
migration filename is recorded for subsequent reviewed schema work; no
application migration is created or deployed by this harness.

Two generated users and 128 KiB of random bytes exercise authenticated upload,
private read, cross-owner/anonymous denial, server-side retained copy,
overwrite/delete protection of that copy, deletion of a synthetic working
object, and restoration of exact bytes from the retained copy. Only aggregate
results and a hash of generated bytes are retained as a one-day artifact.
The isolated project's volumes are removed on exit. User data are never deleted.

This proves a recovery primitive under isolated policies, not the application's
native/Evernote snapshots, tagged note restoration, Task/reminder restoration,
source-evidence separation, cross-device CAS, request replay, migration
verification, authenticated application E2E or WCAG. These remain required
before full migration and release. Sandbox success does not open any gate.

No local invocation: the script refuses non-GitHub/non-Linux execution.
Do not download artifacts or run this stack on the resource-constrained PC.
