## 1. ポジショニング — PRD 非目標との整合 (最重要)

[`PRD.md`](PRD.md) §5 は「⏸ (現時点) 法人向け SaaS・チーム機能 — 個人の経営に集中。事業拡大期に再評価」とする。本提案はこれと**矛盾しない**よう、法人プランを次のように定義する:

| 項目 | 定義 |
|------|------|
| **モデル** | **B2B2C ライセンス一括導入** — 法人が従業員向けの福利厚生・自己啓発支援として個人プロダクトのシートを束で購入する |
| **作らないもの** | チーム共有機能 / 管理者ダッシュボード / 雇用主によるメンバーデータ閲覧 (**新規機能開発ゼロ** = PRD §5 維持) |
| **法人が得るもの** | シート数の一括契約・一括請求 + セキュリティ説明 (本書 §4) + 導入サポート窓口 |
| **従業員 (利用者) が得るもの** | 通常の個人アカウントと同一の体験。**データは個人のもの — 雇用主は閲覧できない** (原則 1・3 / アンチ監視) |
| **再評価トリガ** | `paying-100` 達成前後に法人専用機能 (管理コンソール等) の要否を CEO が再評価 (PRD §5 の「事業拡大期に再評価」を具体化) |

「雇用主が閲覧できない」は制約ではなく**セールスポイント**として打ち出す: 従業員が安心して本音の健康・家計・キャリアデータを書けるからこそ、福利厚生としての利用が定着する。

## 3. 価格表ドラフト (全数値 = CEO 確定待ち)

前提: **MVP 期間は無料公開** ([`MVP_SCOPE.md`](MVP_SCOPE.md) §3 / [`PRESS_RELEASE_V1.md`](PRESS_RELEASE_V1.md))。課金開始は Q4 の Stripe 導入 (`ca38e2d2`) 以降。それまで法人へは「無料 β + 課金開始時に法人契約へ移行」と案内する。

| プラン | 対象 | シート | 価格 (月額/シート) | 含むもの |
|--------|------|--------|--------------------|----------|
| 個人 (B2C) | 個人 | 1 | `【CEO確定: dd9f690b】` | 全コア機能 |
| 法人 S | 小規模導入 | 10〜49 | `【CEO確定】` (個人比 割引率 `【CEO確定】`) | 一括請求 / 導入サポート窓口 |
| 法人 M | 部署導入 | 50〜99 | `【CEO確定】` | 法人 S + セキュリティ説明会 (本書 §4 ベース) |
| 法人 L | 全社導入 | 100+ | 個別見積もり | 法人 M + 請求書払い対応 `【CEO確定】` |

- **構造の原則**: 法人プランの価値は「割引 + 請求一元化 + 安心 (セキュリティ説明)」。**機能差は作らない** (個人と同一機能 / §1)。
- **含まないもの (明記)**: 管理者によるメンバーデータ閲覧 / チーム共有 / 利用強制のための監視レポート (原則 3 違反のため**恒久的に提供しない**)。
- 数値確定の手順: `dd9f690b` 料金プラン v1.0 (個人単価) が先 → 法人割引率を CEO 決裁 → 本表を更新。

## 4. セキュリティ FAQ (実在の実装・運用のみ記載)

営業時にそのまま回答できる Q&A。**本リポジトリで実在確認済みの事実のみ**。未整備の項目は「準備中」と正直に答える。

| # | 質問 | 回答 |
|---|------|------|
| 1 | 認証方式は? | メールアドレス + パスワード (確認メールによる本人確認付き)。Google ログインは feature flag 管理下 (`LANDING_GOOGLE_LOGIN_ENABLED`)。認証基盤は Supabase Auth |
| 2 | 他の利用者・他社にデータが見えることは? | データベースは PostgreSQL の **Row Level Security (RLS)** で行レベル分離 (RLS 有効化 migration 103 件 / deny-by-default 設計 = [`AI_DEV_PRINCIPLES.md`](AI_DEV_PRINCIPLES.md)) |
| 3 | 雇用主 (契約法人) は従業員のデータを見られる? | **見られない**。法人契約はライセンス購入のみで、データは個人のもの (本書 §1 / 原則 1・3)。これは仕様であり方針 — 将来も提供しない |
| 4 | 通信は暗号化されている? | HTTPS (Firebase Hosting 配信 / Supabase API も TLS) |
| 5 | 障害・インシデント対応体制は? | ops 三部作を整備済み: 監視 ([`PRODUCTION_MONITORING_RUNBOOK.md`](PRODUCTION_MONITORING_RUNBOOK.md)) / 障害対応 ([`ONCALL_INCIDENT_SOP.md`](ONCALL_INCIDENT_SOP.md)) / リリース・ロールバック ([`RELEASE_CHECKLIST_ROLLBACK.md`](RELEASE_CHECKLIST_ROLLBACK.md))。エラー監視は Sentry |
| 6 | 開発プロセスの品質管理は? | GitHub Actions による CI/CD。PR は自動 gate (high-risk レビュー gate / minimal E2E gate) を通過しないと merge 不可。本番デプロイは `deploy-prod` workflow で検証付き |
| 7 | SOC 2 / ISO 27001 は取得済み? | **未取得** (正直に回答)。SOC 2 Type 1 は準備タスクとして WBS 化済み (`9a564512` / series-a 段階)。IT セキュリティポリシー v1 策定も計画済み (`bd345cfa`) |
| 8 | データの保存場所・バックアップは? | Supabase (マネージド PostgreSQL) 上で管理。リージョン・バックアップ頻度の契約上の確約は `【確認事項: 契約前に最新仕様を確認して回答】` (口頭で断定しない) |
| 9 | 退会時のデータ削除は? | `【確認事項: 削除フロー最新仕様を確認して回答】` — 確認前に断定しない |
| 10 | AI は従業員のデータで勝手に行動する? | しない。AI は提案のみ行い、**実行可否は常にユーザーが決定** (PRD §4 横断 AI / 原則 1・3)。監視・命令型 AI は非目標として明文化済み (PRD §5) |

**FAQ 運用ルール**: 回答に迷う質問は持ち帰り、本表に追記してから回答する (口頭アドリブで仕様を約束しない)。

## 5. 想定 Q&A / 反論処理 (objection handling)

| 反論 | 返し方 (正直ベース) |
|------|---------------------|
| 「チーム機能がないなら法人で入れる意味は?」 | 意味は「全員に良い道具を配る」こと (福利厚生モデル)。チーム管理が必要なら現時点では対象外と正直に伝える (無理に売らない) |
| 「導入実績は?」 | MVP 公開直後で実績 0。だからこそ βパートナーとして製品に意見を反映できる立場を提案 (§2 slide 10) |
| 「監視レポートが欲しい (誰が使っているか見たい)」 | 提供しない (原則 3)。利用率の集計など匿名・集計レベルの報告は将来検討 `【CEO判断】` — 個人特定は恒久不可 |
| 「サポート体制は?」 | CS 定常運用 (cs-check) は監視 runbook に組込済み。法人向け CS/Onboarding playbook は WBS `6781722f` で整備予定と正直に案内 |
| 「価格を今教えて」 | MVP 期間は無料。課金開始 (Q4) 時の法人価格は確定前 — 「個別見積もり」で対応し、確定し次第連絡 |
