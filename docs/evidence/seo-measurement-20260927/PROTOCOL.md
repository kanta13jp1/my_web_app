# 対象と手順

依頼元: Zennのseo-click-ratio-six-cases。my_web_appのIssue #5563。2026-09-27に本番の匿名日別集計だけを読み取った。対象実装はobservations.jsonのapp_commit。取得SQLを同梱する。生の識別子は取得・公開しない。

python -B scripts/seo_measurement_audit.py docs/evidence/seo-measurement-20260927/observations.json

Pythonは計算・集計用の言語。Flutterはアプリの画面と動作を作る開発用の仕組みで、最後のコマンドは実際の送信処理に人工的な通信応答を与える。外部へアクセスしない。

## 条件と期待結果

1. 入力: 負数、数値文字列、文字、少数、null、真偽値、非有限数、配列、オブジェクトを拒否。0と大きな整数は受理。重複日、不正日、受付との不一致を拒否。欠けた日は0件に補わない。これは新しい読み取り分析器の試験であり、既存の本番受付が同じ入力契約を持つという意味ではない。
2. 日付: 日本の午前0時の直前・直後を分離。夏時間が終わる日の同じ時刻は時差付きなら扱える。時差のない時刻は拒否。本番112件も同じ受付集合でUTCと日本時間の暦日を比較する。UTCは世界共通の基準時刻。重複除外が日本の日付単位のため、UTCで取り直した全記録とは呼ばない。
3. 取りこぼし: 実サービスに通信例外、503、処理拒否、重複相当の応答を与え、続けて新しい操作を成功させる。503はサーバー側で処理できない応答番号。最初の操作が通常終了するか、再送があるか、2回目の成功で過去分も送られるかを観察。過去の欠落件数はこの試験から推定しない。偽の本番アクセスを作らない。
4. 偶然: 7組の同じ曜日の増減を符号検定で調べる。符号検定は増加・減少の偏りを調べる方法。差のない組は除く。独立な組で、増減が半々という仮定のもとで、同程度以上の偏りが出る確率を計算する。今回の分析法は観測後の選択で、事前登録した検証ではない。7通りすべての1組除外も併記し、都合のよい日だけ削除しない。p値を原因の証明や仮説が正しい確率に読み替えない。
5. 季節・需要: 28日分を7日ごとに区切り、欠けた日がある週を除外する。3週では年間季節性を推定できない。検索表示回数のデータは未取得なので、検索需要の効果は未完了。
6. 対照ページ: 公開メモの接触数を同じ期間で照合。0→2で、前期間の基準が0。ページの変更履歴・変更前の並行した傾向・流入条件が未確立なので、有効な比較相手としては採用しない。全体変動を差し引いた因果効果を捏造しない。
7. 因果: 現行のページ比較用サービスはURLで割付を上書きでき、10仮説からの割付を持つ。集計には固定原稿版、上書き操作の除外、露出人数と成果の対応が揃わない。過去14日の増加をAI文章の効果と認定する条件は満たさない。

## 残る実証の実施条件

- 検索需要: 同じ日付・対象ページの検索表示回数を、利用者が管理する検索計測から取得する。アクセス数を検索需要の代用にしない。
- 保存前の損失: 操作発生、送信試行、受付、重複除外、保存の各段階に同じ試験IDを持つ制御試験が必要。過去に記録していない操作数は復元できない。次の実装では端末内の未送信記録と再送期限・同意・消去・重複処理を設計してから本番導入する。
- AI文章の効果: 比較する原稿2版を固定し、文章以外の変更を凍結する。割付・露出・成果を同じ対象単位で計測し、管理者・URL上書きを除外する。主指標、必要標本数、終了日、途中停止条件を事前に固定する。現在の小標本を見て都合よく条件を決めない。
- これらが揃うまで、記事全体の追加7項目は未完了。今回の既存データ監査の結果と、今後の実証を分けて追跡する。
