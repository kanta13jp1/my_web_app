## 本文 (クロスポスト共通版)

### はじめに

「自分株式会社」は Flutter Web + Supabase で構築している AI 統合ライフマネジメントアプリです。Notion・Slack・MoneyForward など 21 の競合サービスが持つ機能を 1 つのアプリに統合することを目標にしています。

2026 年 4 月 1 日時点で Supabase Edge Function は **234 本** に到達。集中タイマー、AI 文章アシスタント、バイラル広告生成、バーチャルペット、AR ナビゲーション……毎日 5〜10 本のペースで機能が拡張されています。

しかしここに至るまで、**「Supabase の 100 関数制限」** という大きな壁がありました。

---

### 問題: 100 本を超えると CI/CD が壊れる

GitHub Actions で `supabase functions deploy --all` を実行すると、100 本超過時点で **402 エラー** が返り、デプロイが失敗するようになりました。

```
Error: Function limit exceeded (402)
Deploy failed: too many functions
```

毎回手動デプロイに切り替えるのは持続不可能なため、仕組みから解決することにしました。

---

### 解決策: Tier 分割デプロイ戦略

採用したのは **Tier 分割** アプローチです。

```
deploy-prod.yml
├── Tier 1A (core): 主要 API 30本 — 毎デプロイで更新
├── Tier 1B (viral): バイラル系 20本 — 毎デプロイで更新
└── Tier 2 (extended): 残り 184本 — 個別 or 手動デプロイ
```

手順の核心は **「Tier 2 の古い関数を事前削除してから Tier 1 をデプロイする」** ことです:

```yaml
- name: Remove stale Tier 2 functions to avoid 402
  run: |
    supabase functions delete old-unused-function || true

- name: Deploy Tier 1A (core functions)
  run: |
    for fn in schedule-daily-digest get-home-dashboard ai-assistant \
               post-x-update health-check daily-judgment; do
      supabase functions deploy $fn
    done

- name: Deploy Tier 1B (viral pipeline)
  run: |
    for fn in viral-share-engine x-media-post viral-video-ad-generator \
               growth-automation-controller landing-ab-test; do
      supabase functions deploy $fn
    done
```

この仕組みにより、Supabase 側でカウントされる関数数が常に 50 本程度に収まり、402 エラーが完全に解消しました。

### バイラル成長パイプラインの詳細

同時期に実装した 5 本の Edge Function によるバイラル成長パイプラインの概要:

#### `viral-share-engine`
ユーザーがコンテンツをシェアした際のバイラル係数 (K-factor) を計算します。招待経由のユーザー数と通常ユーザーのエンゲージメント差を比較し、次のキャンペーン施策の優先度を決定します。

#### `x-media-post`
X (Twitter) への OAuth 1.0a 署名付きメディア投稿を担当します。テキストだけでなく、生成した広告画像も添付できます。

#### `growth-automation-controller`
複数のグロース施策（SNS 投稿、プッシュ通知、メールキャンペーン）のスコアリングと実行順序を管理します。

Flutter 側の呼び出し例:

```dart
// lib/pages/viral_ad_campaign_page.dart
ElevatedButton(
  onPressed: () async {
    final result = await SupabaseClient.instance.functions.invoke(
      'viral-share-engine',
      body: {
        'campaignId': _campaignId,
        'targetPlatforms': ['x', 'instagram'],
      },
    );
    setState(() => _shareScore = result.data['viralCoefficient']);
  },
  child: const Text('キャンペーン起動'),
)
```

### 詰まったポイント 2 選

#### 1. `config.toml` の `major_version` 衝突

ローカル PC・GitHub Actions・Claude Code Web の 3 環境が並行して `supabase db push` を実行すると、`config.toml` の `major_version` フィールドが衝突してマイグレーション失敗が多発しました。

**対策:** `major_version = 17` に全環境で固定し、push 時は常に `--include-all` フラグを使用:

```yaml
- name: Push DB migrations
  run: supabase db push --include-all
```

#### 2. マルチインスタンスによるマイグレーション番号重複

複数の Claude Code インスタンスが同時にマイグレーションファイルを生成すると、同じ番号帯のファイルが重複して生成される問題が発生しました。

**対策:** `CLAUDE.md` にインスタンス別の番号帯ルールを明文化:

```
PowerShell #1〜#5:  000010〜000050
PowerShell #6〜#10: 000060〜000140
Web セッション:     000900〜
VSCode セッション:  000800〜
```

この規約を全インスタンスが共有することで、番号重複ゼロを維持しています。
