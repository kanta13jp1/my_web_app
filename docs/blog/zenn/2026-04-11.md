# Edge Function 94本→15本へ: Action分岐パターンでサーバーレス関数を劇的に削減した話 — 2026-04-11

個人開発の SaaS「自分株式会社」を Flutter Web + Supabase で運営しています。
Notion・Evernote・MoneyForward・Slack など **21 競合の機能を 1 つに統合**するという野心的なコンセプトで、毎週新機能を追加し続けています。

ところが、開発を続けるうちにある深刻な問題に直面しました。

**「Supabase Edge Function が 94 本になってしまった」**

## なぜ 94 本になったか

Supabase の Edge Function は Deno ベースのサーバーレス関数で、機能追加のたびに「1機能 = 1 EF」という設計で増やしていました。

- `ai-university-streaks-get`
- `ai-university-streaks-update`
- `ai-university-badges-issue`
- `ai-university-badges-list`
- ... (90本続く)

気づいたらデプロイが30分かかるようになっていました。

## 解決策: Action 分岐パターン

核心アイデアは「**1つの Edge Function が `action` パラメータで複数の処理を担う**」です。

```typescript
// supabase/functions/ai-hub/index.ts
serve(async (req) => {
  const { action, ...params } = await req.json();
  
  switch (action) {
    case "university_streaks_get":
      return handleStreaksGet(supabase, params);
    case "university_streaks_update":
      return handleStreaksUpdate(supabase, params);
    case "university_badges_issue":
      return handleBadgesIssue(supabase, params);
    // 30+ actions をここに集約
  }
});
```

## Hub 構成: 94本 → 15本

| Hub 名 | 担当ドメイン | 統合した旧 EF 数 |
|--------|-------------|----------------|
| `core-hub` | ユーザー管理・認証 | 12本 |
| `ai-hub` | AI 大学・アシスタント | 18本 |
| `growth-hub` | グロース・競合 | 9本 |
| ... | ... | ... |
| standalone 4本 | 重要な単体 API | — |

**合計: 15本（削減率 84%）**

## Flutter 側の統一クライアント

```dart
// 旧: EFごとに個別URLを指定
final res = await http.post(Uri.parse('$base/ai-university-streaks-get'), ...);

// 新: Hub + action で統一
final result = await EdgeFunctionService().callHub(
  'ai-hub',
  'university_streaks_update',
  {'userId': userId},
);
```

## 詰まったポイント

### 1. Deno の shared モジュール解決

`../shared/` パスがデプロイ時に解決されないケースがありました。

**解決**: `supabase/functions/_shared/` に統一し、必ず `../_shared/` 経由でインポート。

### 2. テスト戦略の変更

HTTP レイヤーのテストは E2E に任せ、**pure-logic テスト**に集中。

```typescript
// ビジネスロジックのみをテスト
Deno.test("ストリーク計算: 連続2日", () => {
  const result = calculateStreak([new Date("2026-04-10"), new Date("2026-04-11")]);
  assertEquals(result, 2);
});
```

今週この方針で **41本のテスト**を追加し、合計 74本体制になりました。

## 結果

| 指標 | Before | After |
|------|--------|-------|
| EF 本数 | 94本 | 15本 |
| デプロイ時間 | ~30分 | ~8分 |
| テスト本数 | 33本 | 74本 |

「制約があるから創意工夫が生まれる」— EF ハードキャップを設けたことで、アーキテクチャが整理されてコードベースが健全になりました。
