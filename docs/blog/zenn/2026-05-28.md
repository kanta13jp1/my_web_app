## はじめに

個人で会社を運営しながらソフトウェア開発をするというのは、エンジニアリングと経営の両方を一人でこなすことを意味します。「自分株式会社」は Flutter Web + Supabase で構築した SaaS アプリで、現在ユーザー数 37 名、機能リクエスト 53 件が積み上がっています。

この規模感では、開発速度が事業の命運を分けます。そこで私が導入したのが「AI エージェント 2 台体制」です。Claude Code と Codex CLI を並列で動かし、それぞれに担当領域を割り当てることで、一人のエンジニアが複数人分の実装速度を出せる仕組みを作りました。

## AI エージェント 2 台体制の構成

私のフリートは以下の 2 台です。

| インスタンス | 役割 | 主なタスク |
|---|---|---|
| Claude Code #1 | アーキテクト兼スクラムマスター | 設計判断・PR レビュー・ブログ下書き |
| Codex #1 | 実装担当 | 機能実装・WBS 更新・アセット管理 |

この 2 台が Git ブランチを介して協調します。Claude Code がアーキテクチャを設計し、Codex が実装するという分業です。これに加えて GitHub Actions で 30 以上のワークフローを自動化しており、毎時のインフラヘルスチェック、AI 大学コンテンツの自動更新、CS チェックなどが無人で動いています。

## Karpathy 4 サイクルによる知識管理

Andrej Karpathy が提唱する「Ingest → Compile → Query → Lint」の 4 サイクルを自社開発に適用しています。

```
Ingest  → scripts/memory_ingest.py
Compile → scripts/wiki_compile.py
Query   → notebooklm CLI（ゼロトークンリサーチ）
Lint    → scripts/knowledge_vault_lint.py
```

これにより「3ヶ月前になぜこの設計にしたのか」を瞬時に呼び出せるようになりました。

## CI ゲートの詰まりと対処法

今週の最大のトラブルは CI ゲートの停止でした。GitHub Actions の PR Gate ワークフローが特定の条件下で `declaration body patch` エラーを吐き、PR が Close/Reopen を繰り返すパターンです。

原因は `GITHUB_OUTPUT` への書き込みタイミングとステップ間の依存関係の競合でした。

```yaml
# After (fixed)  
- name: Check status
  id: check
  run: |
    echo "status=pending" >> "$GITHUB_OUTPUT"
    echo "::notice::Status set to pending"
```

さらに、v21 5 層構造予防仕様（Z-DD アーキテクチャ）を策定。「同日中の自然回復を確認するまでマージしない」ルールで CI の不安定性に対処します。

## 詰まったポイント

**AI エージェント間の文脈共有**

Claude Code と Codex は異なるセッションで動くため、MEMORY.md を Git で共有する仕組みを作りました。毎ターン inject される `~/.claude/hooks/inject-rules.txt` が双方の AI に同じルールセットを適用します。

**GitHub Actions のクォータ管理**

30 以上のワークフローを毎時動かすと GitHub Actions のクォータに当たります。ほとんどのワークフローを Claude 非依存設計にすることで解決。

**Flutter Web の Service Worker キャッシュ問題**

ユーザーからのバグ報告「Loading from existing service worker.」が継続中。`flutter build web --pwa-strategy=none` で回避中。

- AI 2 台体制により 66 コミット/日（自動含む）の速度を維持
- CI ゲートトラブルを v21 仕様で体系化し同日回復ルールを確立
- Karpathy 4 サイクルで知識が資産として蓄積し続けている
