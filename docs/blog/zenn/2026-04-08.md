## はじめに

「自分株式会社」はFlutter Web + Supabase Edge Functions (Deno) で構築したAI統合ライフマネジメントアプリです。Notion・Slack・MoneyForwardなど21社の競合機能を1つに集約しているため、ホーム画面を表示する際に複数テーブルへの問い合わせが同時に発生します。

開発初期は実装の素直さを優先し、クエリを1件ずつ順番に実行するコードを書いていました。しかし機能が増えるにつれて `app-analytics-dashboard` では9クエリ、`blog-post-manager` では14クエリが逐次実行されるようになり、レスポンスタイムが目に見えて悪化してきました。

今回は直近1週間で実施した **「逐次クエリ → Promise.all 並列化」** リファクタリングの実例を紹介します。

## なぜ逐次実行が遅いのか

Supabase Edge Functions は Deno ランタイム上で動き、各クエリは非同期 (Promise) として実行されます。`await` を毎回挟んで逐次実行すると、クエリ間に不要な待ち時間が生まれます。

```typescript
// 悪い例: 3クエリを逐次実行 (合計レイテンシ = A + B + C)
const users = await supabase.from('user_profiles').select('count');
const events = await supabase.from('signup_events').select('count');
const referrals = await supabase.from('referral_events').select('count');
```

それぞれ独立したテーブルへのクエリなので、本来は同時に投げられます。

## 実例1: user-growth-analytics — 3クエリ並列化

```typescript
// Before (逐次: レイテンシ A + B + C)
const usersResult = await supabase.auth.admin.listUsers();
const signupResult = await supabase.from('signup_events').select('*');
const referralResult = await supabase.from('referral_events').select('*');

// After (並列: レイテンシ max(A, B, C))
const now = new Date();
const todayStart = new Date(now.getFullYear(), now.getMonth(), now.getDate()).toISOString();
const weekStart = new Date(now.getTime() - 7 * 86400000).toISOString();

const [usersResult, signupResult, referralResult] = await Promise.all([
  supabase.auth.admin.listUsers(),
  supabase.from('signup_events').select('*').gte('created_at', todayStart),
  supabase.from('referral_events').select('*').gte('created_at', weekStart),
]);
```

ポイントは「時刻境界を事前計算してから全クエリを並列起動する」こと。

## 実例2: app-analytics-dashboard — 9クエリ全並列化

KPI概要ビューで7テーブルのカウント + `recentUsers` + `funcStatus` を1段の `Promise.all` に統合しました。

```typescript
const [userCount, noteCount, taskCount, goalCount,
       habitCount, requestCount, achievementCount,
       recentUsers, funcStatus] = await Promise.all([
  supabase.from('user_profiles').select('*', { count: 'exact', head: true }),
  supabase.from('notes').select('*', { count: 'exact', head: true }),
  supabase.from('tasks').select('*', { count: 'exact', head: true }),
  supabase.from('goals').select('*', { count: 'exact', head: true }),
  supabase.from('habits').select('*', { count: 'exact', head: true }),
  supabase.from('feature_requests').select('*', { count: 'exact', head: true }),
  supabase.from('development_achievements').select('*', { count: 'exact', head: true }),
  supabase.from('user_profiles').select('id,email,created_at')
    .order('created_at', { ascending: false }).limit(10),
  supabase.from('edge_function_ui_status').select('*').order('function_name'),
]);
```

逐次3段 → 1段。ラウンドトリップ数が劇的に減少します。

## 実例3: blog-post-manager — 14クエリを3段並列に

メインリスト + 11プラットフォーム別カウント + 今日の投稿数の合計14クエリを並列化しました。

```typescript
const todayStr = new Date().toISOString().slice(0, 10);

const [postsResult, ...platformCounts] = await Promise.all([
  postsQuery,
  ...PLATFORMS.map(p =>
    supabase.from('blog_posts')
      .select('*', { count: 'exact', head: true })
      .contains('target_platforms', [p])
  ),
  supabase.from('blog_posts').select('*', { count: 'exact', head: true })
    .gte('created_at', todayStr),
]);
```

14クエリ逐次 → 実質1ラウンドトリップ相当に。

## 詰まったポイント

### エラーハンドリング

`Promise.all` は reject が1つでも全体が失敗します。Supabase JS クライアントは `{ data, error }` を返すので通常は reject しませんが、`auth.admin.listUsers()` 等は throw することがあります。

```typescript
try {
  const [usersResult, signupResult] = await Promise.all([...]);
  if (usersResult.error) throw usersResult.error;
} catch (err) {
  return new Response(JSON.stringify({ error: err.message }), { status: 500 });
}
```

### deno lint 対応

並列化後に `?.` (Optional chain) を外して `?? []` に統一すると `deno lint` がクリーンになります。destructure した変数の型が明確になるためです。
