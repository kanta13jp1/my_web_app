# 残響ポンプ室の独立ビルド・配信試作

第3段階は、既存の専用fixtureを別のFlutterアプリ入口としてreleaseビルドし、独立した静的成果物で配信できるかをCI内で確かめる。
コード・認証・DB・本番公開の分割はこの試作に含めない。

手動`echo-pump-prototype.yml`の`profile=release-prototype`に固定SHAを指定する。
通常と専用は同じSHA、Flutter 3.38.x、release、PWA無効、ローカルWebエンジン、同じbase href・合成接続先を使い、別の新しいランナーで各1回測る。
依存準備とキュー待ちは除外する。全ファイルのサイズ・SHA256、main.dart.jsの元サイズとgzipサイズを記録する。
既存indexのbase hrefは固定値のため、CI内のビルド時だけFlutterのプレースホルダーへ置換し、終了時に元のバイト列へ復元して確認する。本体ソースの変更はコミットしない。
pubspec・依存関係・アセット宣言は共有のままで、入口を変えるだけで全アセットが減るとは仮定しない。

ビルド後は`/prototype/echo-pump/`へ置いたものとしてHTTP配信し、PCと狭幅で表示・ゲーム開始・直接再読込・ブラウザーでホストへ戻る操作を確認する。
外部ネットワークはフォントHTTPSだけ許可し、通常入口のバックエンドは合成応答に限定する。
専用側のbuild/webをtarへ保存し、BUILD.jsonのハッシュとともに、既存本体と別に保管できる成果物にする。本番へはアップロードしない。

fixtureのホームは実際の本体への戻り先ではない。CIホストページへのブラウザー戻りは本番ナビゲーションの統合試験の代わりにはならない。
本番導入前に、共有テーマ・ログイン/セッション不要の確認・ページ移動/戻り・SEO・アセット配信・版管理・監視とロールバックを具体化する。
現時点の戻し方は本体の既存`/echo-pump`を維持し、試作の配信物を採用しないこと。既存ルートは変更しない。

単回ビルド差だけで採用を決めず、独立配信の運用負担と全体ビルドの必要頻度も比較する。
手動試作は既存PR full検証を減らさない。
